Domains: DNS is checked before anything is signed, and what else can stop a deploy
Approved on 2026-11-19. A stop before signing prints the sentence alone, as every such stop does today.
New · no record yet
It stops before signingzekno deploy
$ zekno deploy
✖ shop.example.com has no DNS record yet.
Create an A record for shop.example.com with the value 203.0.113.7, then run zekno deploy again.
Nothing was signed.
The commonest first mistake. Nothing was signed or sent; the sentence names the exact record.
New · it points somewhere else
It stops, and names the way pastzekno deploy
$ zekno deploy
✖ shop.example.com points to 198.51.100.9, not to prod-1.
Change its A record to 203.0.113.7, then run zekno deploy again. If something of yours stands in
front of prod-1, deploy with --skip-dns-check. Nothing was signed.
--skip-dns-check is for a CDN or a proxy of your own in front of the server, where DNS rightly answers with another address.
New · warnings: the deploy goes on
Two warningszekno deploy
$ zekno deploy --skip-dns-check
! DNS was not checked for shop.example.com.
$ zekno deploy
! shop.example.com points to 198.51.100.9, no longer to prod-1. Visitors are not reaching shop
there, and its certificate cannot be renewed.
Above: the check was skipped on purpose. Below: a domain the app already holds has moved away. It is not a reason to stop a deploy of new code, but it is said every time.
New · zekno cannot tell
The server is reached at a private addresszekno deploy
$ zekno deploy
! zekno cannot tell whether shop.example.com points to prod-1, because this machine reaches prod-1
at an address that is not public. It points to 203.0.113.7.

New · the domain is another app's
One app holds a domainzekno deploy
$ zekno deploy
✖ shop.example.com belongs to blog on prod-1.
Release it there first: run zekno domain rm shop.example.com in blog's folder and deploy blog.
Nothing was signed.
The server tells zekno which app holds each domain, so this stops before signing and names the app. Moving a domain is two deploys: release, then claim.
New · the runner is too old
Update the runner firstzekno deploy
$ zekno deploy
✖ The runner on prod-1 is version 0.1.0, too old for domains and health checks.
Run zekno server update prod-1, then run zekno deploy again. Nothing was signed.
Only when the deploy has a domain or a health check. A deploy without either keeps working with the older runner.

✖ shop is running, but prod-1 cannot answer for its domains: port 80 is in use by another program.
Free ports 80 and 443 on prod-1, then run zekno deploy again.
The server could not start its proxy. The app itself is running as deployed.
The other sentences, in the same pattern
A service with a domain has no port
web has a domain and no port. Set the port it listens on with zekno settings set web.port <port>. Nothing was signed.
A rollback to a deploy without the routed service
What deploy 41 ran has no service named web, which shop.example.com reaches. Remove the domain first, or roll back to a deploy that has web. Nothing was signed.
A routed service has no container
shop.example.com cannot reach web: no container of web is running. Run zekno logs to see why.
A routed service uses the host's network
shop.example.com cannot reach web: web uses the host's network, which zekno cannot route to. Give web a network of its own, then run zekno deploy again.
The proxy did not take the new domains
shop is running, but prod-1 did not take its new domains, so it answers for the ones it had. Run zekno doctor to see why.
The runner refuses: the domain is another app's (two deploys at the same moment)
A domain of this deploy belongs to another app on that server. Nothing of it ran. Run zekno domain to see which.
The runner refuses: too many domains on the server
That server would hold more domains than a runner keeps. Nothing of this deploy ran. Remove a domain from an app there first.
