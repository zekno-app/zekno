Files a build fetches
zekno refuses an ADD line that fetches from the server itself or from a private address. It reads only the address as written: a name that leads to a private address on the server, or a public address that redirects to one, is not caught. What holds a fetched file to its content is the checksum every such ADD line must carry.

Secrets in a build
A build reads a secret only when its settings name it, one by one, and you agreed on this machine. zekno asks once for each secret, service, app and server, and not again when the recipe changes. The secret stays on your server, so Zekno cannot read it. But it travels further on the server than today: it is handed to steps that run other people's code and download from the internet. A build that reads a secret and has the network can send it anywhere, and no signature prevents it. A step that copies it into a file puts it in the image. A step that prints it puts it in the build's output: in Docker's record of the build on the server until the runner removes it, in the output zekno saves on your machine, and with no terminal in whatever log reads standard error. A step that writes it into a cache folder (RUN --mount=type=cache) leaves it there for later builds of the app, even builds that read no secret and reuse no cached step.
RUN --mount=type=secret,id=NPM_TOKEN npm ci

What is signed
The signature covers the code, the recipe, the builder and its version, the plain variables the build reads with their values, the names of the secrets it may read, its network and its time limit. It does not cover what the build downloads while it runs: for a Dockerfile, base images named by tag and what its steps fetch. Nor does it cover the server's Docker and builder versions, base images already on the server, or steps reused from the server's build cache, which every app on the server shares. Network none applies to the build's own RUN steps only: the builder still fetches base images, and files that ADD names by URL.

Building from source
What is built is signed: the code, the recipe (the Dockerfile's path and stage), the builder and its version, the plain variables the build reads and the names of the secrets it may read. The code travels sealed for the server, so no other machine can open it. The server holds the code in plain text, in Docker's storage and in the image. What the builder prints can quote the code; it goes only to the zekno that deployed, and the runner keeps none of it. See what the signature covers.

What is signed
The signature covers the code, the recipe, the builder and its version, the plain variables the build reads with their values, the names of the secrets it may read, its network and its time limit. It does not cover what the build downloads while it runs: for a Dockerfile, base images named by tag and what its steps fetch; for Railpack, the packages and language tools its steps fetch. Nor does it cover the server's Docker and builder versions, base images already on the server, or steps reused from the server's build cache, which every app on the server shares. Network none applies to the build's own RUN steps only: the builder still fetches base images, and files that ADD names by URL.
Variables in a build
A Dockerfile build reads the plain variables of its service that it declares with ARG, and no other. A Railpack build reads every plain variable of its service, at most 32. A plain variable given to a build is signed, readable by whoever relays the deploy, as it is in the settings, and stays readable in the image's history of a Dockerfile build. A secret never reaches a build through ARG.

Railpack
Railpack is a program made by Railway, a third party. zekno fetches the one version it pins from Railpack's own release, checks it against a checksum zekno carries, and runs it on your machine, with your rights, on the files it would send. It reaches the network to find language versions, so each deploy with Railpack needs the network. Its plan decides what the server runs. The checksum makes every machine run the copy the maintainer approved. It does not make that copy safe. The image Railpack builds runs as root inside its container, and starts through a shell.

Protocol 3
Deploy format 2 also has fields for a command to run before a deploy. The runner does not carry it out, and refuses a deploy that uses it. Protocol 7 means the runner also builds with Railpack, from the plan signed with the deploy, with the Railpack image whose digest is signed.
