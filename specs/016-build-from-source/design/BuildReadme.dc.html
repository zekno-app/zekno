Scenario
Why

One of your servers is compromised
Secrets are plaintext in memory where the app runs, and the server holds the TLS keys of its domains and, for an app built there, its code, in Docker's storage and in the image

What a build downloads while it runs
Base images named by tag, packages are fetched on the server during the build. No signature covers them.
A build that runs out of memory
A build shares the server's memory, processor and disk with the apps already running there. One that runs out of memory can make the server stop other programs, the running app among them.

Note
The control plane, when it exists, will never see a secret's value. It will see:
•Server addresses and team membership
•App names, deploy numbers and times
•Each deploy's Compose text with its plain variables, and image names with their digests
•Each secret's name, version, size and who set it
With domains, building from source and health checks, it will also see:
•Domains
•Build recipes and their arguments, pre-deploy commands, health-check paths
•The size and fingerprint of each source pack: enough to confirm a guess of the exact source (a public repository at a known commit), not to read it

Note
The control plane, when it exists, will never see a secret's value. It will see:
•Server addresses and team membership
•App names, deploy numbers and times
•Each deploy's Compose text with its plain variables, and image names with their digests
•Each secret's name, version, size and who set it
With domains, building from source and health checks, it will also see:
•Domains

The code travels sealed for your server, and what the builder prints travels sealed for the person who deployed, or not at all.

Building from source
What is built is signed: the code, the recipe (the Dockerfile's path and stage), the builder and its version, the plain variables the build reads. The code travels sealed for the server, so no other machine can open it. The server holds the code in plain text, in Docker's storage and in the image. What the builder prints can quote the code; it goes only to the zekno that deployed, and the runner keeps none of it. See what the signature covers.

What Zekno does not protect against
Scenario
Why
What a build downloads while it runs
Base images named by tag, packages and language tools are fetched on the server during the build. No signature covers them.
Railpack, which zekno fetches and runs on your machine
Railpack, at the version zekno pins, and the image it builds with on the server, are trusted as zekno is. Railpack runs with your rights on the machine that signs, and its plan decides what the server runs. The checksum makes every machine run the copy the maintainer approved. It does not make that copy safe.
