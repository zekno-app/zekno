Building from source
zekno deploy in a folder of code: what is sent, what is signed, how the server builds it, and what the signature covers and does not.
What is signed
The signature covers the code, the recipe, the builder and its version, the plain variables the build reads with their values, its network and its time limit. It does not cover what the build downloads while it runs: for a Dockerfile, base images named by tag and what its steps fetch. Nor does it cover the server's Docker and builder versions, base images already on the server, or steps reused from the server's build cache, which every app on the server shares. Network none applies to the build's own RUN steps only: the builder still fetches base images, and files that ADD names by URL.
What is sent
zekno sends the folder's files, except those .dockerignore lists, as docker build would. It never sends a link. It leaves out .git unless the settings name it, and every file that looks like it holds secrets unless the settings name it and you agreed to it on this machine. That list holds .env and .env.* in any folder, .npmrc, .netrc, .git-credentials, and files whose name or content marks a private key. It is a convenience, not a guarantee: a secret in a file of another name is sent.
What the server holds
The server holds the code in plain text, in Docker's storage and in the image. Docker's builder keeps a record of each build, with its output and its build arguments, until the runner removes it after the build. What the builder prints can quote the code, and holds anything a step prints. The runner keeps the images of the deploy each app runs and of its two latest other builds, and brings the build cache to 10 GiB after each deploy. That pruning also reaches builds made outside Zekno on the same server. An older runner put back by hand refuses to act; the way back is to update the runner again.

Memory and disk
A build shares the server's memory, processor and disk with the apps already running there. A build that runs out of memory can make the server stop other programs, the running app among them. zekno does not limit a build's memory in this version. A build does not start below 2 GB of free disk, and stops if it falls below it. What a server with 1 GB of memory does during such a build has not been measured.
Docker on the server
Building needs Docker Engine 29.5 or later on the server, with its build plugin. zekno doctor --builds says whether a server can build. A server that cannot build still runs apps from images. A base image in a private registry works when the server's Docker is logged in to it.
Variables in a build
A Dockerfile build reads the plain variables of its service that it declares with ARG, and no other. A plain variable given to a build is signed, readable by whoever relays the deploy, as it is in the settings, and stays readable in the image's history of a Dockerfile build. A secret never reaches a build through ARG.
What was checked, and where
Each finding of the checks on Linux, with where it ran: GitHub's Linux machines, a throwaway Linux container, or the maintainer's own server.

Metadata
The control plane, when it exists, will never see a secret's value. It will see:
•Server addresses and team membership
•App names, deploy numbers and times
•Each deploy's Compose text with its plain variables, and image names with their digests
•Each secret's name, version, size and who set it
With domains, building from source and health checks, it will also see:
•Domains
•Build recipes and their arguments, pre-deploy commands, health-check paths
•The size and fingerprint of each source pack: enough to confirm a guess of the exact source (a public repository at a known commit), not to read it

Protocol 5
The runner stops waiting for docker compose up after 30 minutes, and the result of deploy then says so, with startLimit (see A start that does not finish).
Protocol 6
Protocol 6 means the runner also builds an app from source with a Dockerfile: it checks the sealed code against the signature, then builds the image with the server's own Docker (see Building from source). A deploy can end with one more outcome, after its number is used: build_failed, with its reason.
