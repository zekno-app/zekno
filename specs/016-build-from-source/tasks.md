# Tasks: Build from source (feature 016)

**Input**: [plan.md](./plan.md) ("Phases", "Needs the maintainer", the 29 items decided on 2026-11-27), [spec.md](./spec.md) (131 requirements, US1 to US12, maintainer steps M1 to M10), [data-model.md](./data-model.md), [quickstart.md](./quickstart.md) (the checks L1 to L18 with L4b, R1 to R10 and R16, B1 to B6, the jobs, "Results"), [contracts/core.md](./contracts/core.md) (CO1 to CO19), [contracts/runner.md](./contracts/runner.md) (RB1 to RB18), [contracts/cli.md](./contracts/cli.md) (CL1 to CL14), [research.md](./research.md) and the maps in [research/](./research/), [design/lines.md](./design/lines.md) (every sentence by its row) and [design/README.md](./design/README.md) (which board draws which rows).

Tests are part of each task: a test that fails first wherever a contract fixes the behaviour, and a test of every branch (the constitution, Principle VII). `[P]` marks a task that touches other files than its neighbours. A story label names the one story that owns a task; a task with none serves several, or none. Rows such as A1 or G26 are those of `design/lines.md`; CO, RB and CL are the parts of the three contracts; L, R and B are the checks of `quickstart.md`.

Stories: US1 deploy a folder that has a Dockerfile (P1, step 1); US2 know what is sent before anything is signed (P1, step 1); US3 follow a build, and a failed build leaves the app alone (P1, step 1); US4 only what a team member signed is built (P1, steps 1 and 2); US5 nothing changed, nothing sent, nothing built (P2, step 1); US6 deploy a folder that has no Dockerfile (P2, step 2); US7 build settings where a Railway user looks for them (P2, steps 1, 1b and 2); US8 roll back to a built deploy (P2, step 1); US9 a server's disk stays in check, and doctor says when a server cannot build (P3, step 1); US10 old and new programs say what to do (P2, steps 1, 1b and 2); US11 a build reads the service's plain variables (P2, steps 1 and 2); US12 a build reads only the secrets named for it (P3, step 1b).

**Rules every task keeps**:

- No package is added to any `package.json`. The readers of `.dockerignore`, Dockerfiles and `.git` are written in the project; compression is Bun's built-in zstd (`node:zlib`).
- Every module lives in a folder named for its subject, and its tests mirror it. No file passes 500 lines. No folder is named `build`.
- In `apps/cli`, every bun command is `bun --no-env-file ...`. `apps/cli/.env.local` is never read, printed or copied. `apps/cli/e2e.config.ts` and `apps/cli/tests/` are not edited. `apps/cli/test/plain/plain-unchanged.test.ts` is frozen: its only change is the four new help lines appended to its existing list (plan item 24). In `apps/cli`, never call a package script that starts another bun: the `screens` script is `bun test/screens/capture.ts`, so `bun --no-env-file run` of it starts an inner bun that does not get the flag and reads `.env.local`. The screens are captured with `bun --no-env-file test/screens/capture.ts <name>` and checked with `bun --no-env-file test/screens/capture.ts --check`.
- The program on the server is "the runner", never "agent". Public docs, the READMEs and the site never say "desktop app" or "dashboard". Docs pages and the READMEs are no longer than 500 lines, the bound `apps/web/modules/docs/lib/pages.test.ts` holds (it fails past 500).
- Every sentence a person sees comes from `design/lines.md` by its row, exactly. A row in lines.md's last section, "Written after the approval of 2026-11-27", is a draft: the task that builds it is blocked until the maintainer approves `BuildNewLines` (step 1) or `BuildNewLinesLater` (steps 1b and 2). Screens and lines come last within each step, after the logic under them.
- A task whose shape depends on a check's result says so ("After L2") and what it builds on each result. It never guesses the result.
- Real Docker on the maintainer's Mac runs only in the Linux stand-in, or with a builder state of its own (a private `BUILDX_CONFIG` and a throwaway container). It removes what it made and never touches containers, images or build records it did not create: an earlier test on this Mac made Docker drop the maintainer's own build history. Ports 3000 and 3100 are never used. `next dev` and `next build` are never run. Tests never use the real keychain or `~/.zekno` (`memoryKeyStore()`, a temporary `ZEKNO_HOME`).
- Outward steps are the maintainer's, each with its own go-ahead at the time, and are listed under "Maintainer steps", not as tasks: pushing the branch, a ruleset, a merge into `dev` or `main`, a release tag, a second build, approving a release, any use of the maintainer's own server, and the fetch of Railpack's checksums on the Mac's network (M3). Releases are 0.1.2-dev.1 and 0.1.2-dev.2; `main` never holds a dev version. No task commits, pushes, tags or checks out.

A blocked task says so at the start of its text, in bold.
