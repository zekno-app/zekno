<Callout type="warn" title="Pre-alpha and unaudited">
  The command-line tool, the runner and the core library have had internal
  reviews only. Do not use them for anything you could not afford to lose, and
  do not rely on them in production before an external audit.
</Callout>

`zekno` deploys Docker Compose apps to servers you own. Secrets are encrypted
and deploys are signed on your machine. The [runner](/docs/runner), a program
on your server, checks every signature before it decrypts or starts anything.

Run `zekno` alone at a terminal and a full-screen app opens. Everything the app
does is also a single command, for scripts.

An app is deployed from a Compose file you write, or from its settings in
`zekno.app.json`, which `zekno` turns into Compose text on your machine and
signs. See [zekno settings](#zekno-settings).

## Status and limits

- **One developer on one machine.** Teammates arrive with the control plane,
  which is not written yet.
- **SSH is the route.** `zekno` talks to the runner directly, over SSH. No
  Zekno service is involved.
- **Only `zekno version` and `zekno doctor` reach the network on their own:**
  each asks GitHub once for the newest release, and sends nothing about you.
- **State and logs come from your server.** Whether an app is running, and its
  logs, are read from the runner over SSH when you look. They never pass
  through Zekno, and your machine keeps none of it.
- **The runner comes from a release.** `zekno server add` installs on a
  server the one runner version your build of `zekno` carries, and only when
  it matches the checksum that build holds. A `zekno` built from `main`
  installs a prod release, such as `0.1.0`; one built from `dev` installs a
  development release, such as `0.1.0-dev.1`. See
  [Installing the runner](#installing-the-runner).
- **The first runner release is 0.1.0.** A `zekno` built from `main` holds its
  checksums and installs it on a server by itself. Between a release being
  started and its second build, a `zekno` built from that branch holds no
  checksums and says it has no published runner to install.
- **Docker's messages are shown as they are.** An error from Docker can repeat
  a value that was filled in from a secret.
- **App settings cover an image that is already built.** This version cannot
  build an image from source, serve a domain with HTTPS, wait for a health
  check, run a command before a deploy, or run several copies of a service. A
  `zekno.app.json` that sets one of them is refused with a sentence that names
  it. A Compose file written by hand can do what Compose does.
- **A published port is open to whoever can reach the server.** It is
  published on every address of the server, as Compose does, and Docker's
  published ports can pass a host firewall such as `ufw`. Zekno does not
  manage the server's firewall.
- **"Changed, not deployed" knows only your machine's deploys.** A teammate's
  later deploy from another machine is not seen.
- Made for macOS and Linux with a system keychain. Windows is not tested.

The internal security reviews, which say what was checked and what was not,
are in the `specs` folder of the
[repository](https://github.com/zekno-app/zekno).

## Build from source

`zekno` is not packaged for installation yet. It needs [Bun](https://bun.sh)
1.4.4, the version pinned in the repository.

```bash
bun install                  # at the repository root
bun apps/cli/src/main.ts     # runs zekno from the checkout
cd apps/cli && bun run compile   # dist/zekno: one file, for the system you are on
```

Run from the checkout, `zekno` reads `.env` and `bunfig.toml` from the folder
you start it in, because that is how Bun runs a script, and a `bunfig.toml`
can make it load other code first. The runner it starts from `apps/runner`
for `--local` does the same. So run it from source only inside folders you
trust, and use the compiled `zekno` anywhere else: it is built with both
turned off, and a test in the repository checks that it reads neither. Like
any program built with Bun, the compiled `zekno` still obeys three of Bun's own
variables: `BUN_OPTIONS` (for example `--preload <file>`, which runs that file
first), `BUN_BE_BUN=1` (it then acts as Bun itself) and `BUN_INSPECT` (it opens
a debugger). Whoever can set them already controls your account.

From a checkout, `zekno server add --local` starts the runner from
`apps/runner` next door. The compiled `zekno` starts `zekno-runner` from your
`PATH` instead.

## The app

`zekno` with no arguments, at a terminal, opens a full-screen app. Without a
terminal (piped, in a script, or with `TERM=dumb`) it prints the help and
exits with status 2.

The window must be at least 80 columns by 24 lines. In a smaller one the app
asks for a larger window, and comes back to the same screen when there is
room. Each screen lists its keys on its last line. When you quit, the terminal
is left as it was, also after an error.

| Screen | Opens from | Shows |
| --- | --- | --- |
| Home | Start, when a team exists | Servers; the selected server's apps with deploy number, state and when; the selected app's details and actions; whether this folder is linked |
| App | `enter` on an app | Deploy history; secrets by name and version; the selected deploy's details; a note when a secret is newer than the running deploy |
| Deploy | `d`, or `r` | Summary panel, stage row, one live line; Docker's output on `o` and on failure |
| Logs | `l` | Time, service, text; following or paused |
| First run | Start, when no team exists | The logo, the three steps (your key, a server, a first deploy), the name question |
| Add a server | `a` on Home, or step 2 of first run | The destination and name, each step as it completes, the team code and the server code with what each is for. Once done it stays, every step ticked and the server code shown, until `enter` goes to Home |
| Set a secret | `s`, or before a deploy when values are missing | The names that are missing, the hidden prompt |
| Settings | `e` on an app | This folder's `zekno.app.json`, one service at a time, in sections; on `c`, the Compose text it turns into. See [The settings screen](#the-settings-screen) |
| Help | `?` | The app's keys, in groups. `e` and the keys of the settings screen are on their hint lines, not in help |

A profile that does not verify opens an error screen with the reason instead
of Home. Only `q` and `ctrl-c` work there.

### What is running, and keeping in touch with servers

- Home and the App screen show each app as `running`, `stopped`,
  `partly running` or `unknown`, by a word and a symbol as well as a colour.
  An app is running when every service runs, stopped when none does, and
  partly running otherwise.
- State is read when a screen opens and every 5 seconds while Home or App is
  showing: Home reads every server, App its own. Nothing is read while a
  question is open, below 80 by 24, or while the app is quitting.
- When the app starts, it opens one session to each server: one SSH connection
  to the runner, kept open while the app runs. That is the moment SSH may ask
  for a password. Each read sends its requests over that session, so a read
  adds no SSH login. One read per server at a time.
- A read with no answer within 20 seconds, or a session that ends, closes that
  session. The server is then shown as not reached, with the reason, and its
  apps' state as unknown. Its apps keep the deploy numbers your machine has.
- A server whose session was lost is connected to again in the background, at
  most once every 30 seconds, in SSH's batch mode only: it never asks for a
  password and never takes over the terminal.
- Where SSH would have had to ask (a password, a key passphrase, a host key)
  and was not answered, the server is marked `!` instead of its dot, with "needs an answer" under its name, and its apps' state is unknown. It is not
  tried in the background again until you connect to it on purpose: `enter` on
  it in the servers pane (the hints say `enter connect`), or start the app,
  deploy, roll back, open logs, update or add. A server that refuses the
  connection, does not answer in time or does not resolve is shown as not
  reached (`✖`).
- `enter connect` tries SSH's batch mode, then hands the terminal over so SSH
  can ask, checks that it is the server you connected, and keeps the session
  for the reads that follow. If you cancel at SSH's question, the mark stays.
- Deploys, rollbacks, secrets and logs use connections of their own, never the
  kept session.
- After a server is added from the app, the session it was added over is kept,
  so SSH does not ask a second time.
- A runner that does not report its version has no sessions. It is read when
  the app starts and after `u`, never in the background.
- Every kept session is closed when the app closes, on `q`, an error or a
  signal.
- If SSH has to ask for a password or a host key, the app first tries SSH's
  batch mode, then hands the terminal over so you can answer on the normal
  screen, and takes it back once the connection is up.

### Deploying from the app

- A folder linked by a `zekno.json` signed by your team and in use on your
  machine deploys at once to its own app on its own server, and on its own server with no apps. With
  another app selected, on its own server or another, `d` first asks: "This
  folder is linked to web on dev. You selected billing. Deploy this folder to
  billing? It replaces what billing runs now." Only `y` deploys the folder's
  file to the selected app; `n` or `esc` ends with "Nothing was deployed.",
  and `enter` does nothing. Nothing is read from the keychain, signed or sent
  before `y`, and `zekno.json` is not changed. On another server with no apps,
  `d` says so and deploys nothing. One exception: on its own server, a linked
  app that has never been deployed there has no row to select yet, so `d`
  deploys it as its first deploy whichever row is marked. No other app is
  replaced.
- `d` deploys the file `zekno deploy` would: the one a linked folder's
  `zekno.json` names, which may be `zekno.app.json`, or in a folder that is
  not linked the one of `compose.yaml` and `zekno.app.json` that is there.
  With both there and no `zekno.json`, `d` deploys nothing and says
  `This folder has zekno.app.json and compose.yaml. Run zekno link -f <file> here to say which.`
  Neither is ever picked over the other without you saying so.
- A folder with no `zekno.json` deploys its file to the selected app. Before
  the first deploy, the app asks whether to remember the folder; yes writes
  `zekno.json` naming that file, signed with your key, and records it as used
  here. With no app selected, it points you to `zekno link`.
- A folder whose `zekno.json` is not signed by your team deploys nothing, and
  Home says why. One signed by your team that was not used here before is
  asked about when the app opens; until you say yes, `d` deploys nothing and
  says so.
- The file is read once, when `d` is pressed. A settings file is turned into
  its Compose text then, and a fault in it is said on the status line before
  any question; nothing is deployed. The names listed and the text signed
  come from that one read.
- Before a deploy, names the Compose text expects that have no secret are
  listed, at most 64. Each can be set with the hidden prompt, or the deploy
  can go ahead without them. At the prompt `esc` returns to the list and signs
  nothing. On the list `esc` asks before deploying without them; "no" ends
  with "Nothing was deployed.".
- `esc` during a deploy returns to the screen before; the result arrives there
  as a line. `q` waits for the deploy to finish, then closes.
- The deploy screen shows a summary panel, a row of stages (checked, signed,
  sent, starting, then started or failed) and one live line. Docker's full
  output is shown on `o`, and on a failed start.

### The settings screen

`e` on an app's screen opens its settings: the settings `d` would deploy for
that app from the folder the app was started in. That is the `zekno.app.json`
of that folder, or the settings file its `zekno.json` names when the folder is
linked to that app on that server. See [zekno settings](#zekno-settings) for
the file.

```text
╭────────────────────╮ ╭─────────────────────────────────────────────────────────────────────────╮
│ Services           │ │ web                                                      zekno.app.json │
│ ❯ web              │ │ Source                                                                  │
│   worker           │ │   image      ghcr.io/acme/demo-web:1.4.2                                │
│                    │ │ Deploy                                                                  │
│                    │ │   start      bun run start                                              │
│                    │ │   restart    on failure                                                 │
│                    │ │ ❯ memory     1g  ! changed, not deployed (was 512m)                     │
│                    │ │   cpus       1                                                          │
│                    │ │ Networking                                                              │
│                    │ │   port       3000                                                       │
│                    │ │   published  not published                                              │
│                    │ │ Variables                                                               │
│                    │ │   secrets    DATABASE_URL, SESSION_KEY                                  │
│                    │ │   plain      NODE_ENV=production                                        │
│                    │ │ Volumes                                                                 │
│                    │ │   uploads    /data/uploads                                              │
│ One app, one file: │ │ ─────────────────────────────────────────────────────────────────────── │
│ zekno.app.json     │ │ A change is written to the file. It runs after the next deploy.         │
╰────────────────────╯ ╰─────────────────────────────────────────────────────────────────────────╯

↑↓ move  enter change  tab services  c Compose text  d deploy  esc back
```

- The left pane lists the file's services. The right one shows one service in
  five sections: Source, Deploy, Networking, Variables, Volumes. Every setting
  has a row, set or not. One not set reads dim: `the image's own` for the
  start command, `no` for restart, `no limit`, `none`, or `not published`.
  Secrets are shown by name only.
- `! changed, not deployed (was 512m)` marks a value that differs from your
  machine's last deploy of that app, when that deploy was made from settings.
  When that is not known, nothing is marked.
- What that deploy had and the file no longer has is marked as
  `zekno settings` marks it: a variable or a volume is a row
  `none  ! removed, not deployed (was …)`, a volume adding `; its data stays`,
  and a service is listed under the others in the Services pane with
  `! removed, not deployed`.
- A value longer than three lines is cut there, and the line under it says
  how many more there are and where they are:
  `… 52 more lines: c shows them in the Compose text`. The box of a change
  shows the old and the new value whole when they fit, else each cut with the
  same line.
- `↑` `↓` move between settings, `enter` changes the selected one, `tab` shows
  the next service, `c` shows the Compose text the settings turn into (`c` or
  `esc` goes back), `d` deploys as on the app's screen, and `esc` goes back to
  the app's screen.
- `d` here deploys only the file the screen shows. When it changed since,
  nothing is deployed, the status line says
  `The settings changed since this screen showed them, so nothing was deployed.`
  and the screen shows the file as it is now.
- **Changing a value.** `enter` opens a box with the setting's current value
  filled in. Type the new one and press `enter`; `restart` is a list to choose
  from. A value its rule refuses shows the rule, and the box stays open. An
  empty value removes a setting that can be left out; the image cannot be.
  Then the box shows `now` and `new` and asks "Write this to zekno.app.json?
  Nothing is deployed until you deploy." Only `y` writes it. It is written as
  `zekno settings set` writes it, and runs after the next deploy.
- A plain variable or a volume is added with `zekno settings set`; `enter` on
  their `none` row says how.
- While no change is open, the file is read again every 5 seconds, so an edit
  made elsewhere shows. A change confirmed after the file changed is not
  written, and the status line says so.
- In place of the settings, one sentence when the folder has no settings file,
  when it deploys a Compose file, when it is linked to another app, or when
  the file has a fault. Linked to another app, it reads:
  `This folder is linked to <app> on <server>. Its settings are on that app's screen.`
- In a folder that is not linked and has both `zekno.app.json` and
  `compose.yaml`, the settings are shown, and `d` deploys nothing and says to
  run `zekno link -f <file>` there to say which file.
- At 80 by 24 the rows that do not fit are said as `↑ <n> more` and
  `↓ <n> more`.
- Reading the settings and writing a change read nothing from the keychain and
  contact no server. The app's state in the header is read from its server, as
  on the app's screen.

### Logs in the app

The logs screen follows an app's logs over a connection of its own. It keeps
the last 2000 lines in memory and writes nothing to disk. It says where they
come from: "Read straight from your server over SSH. Nothing passes through
Zekno." When the connection drops, it says so, and `enter` connects again.

## Commands

```text
zekno init --name <you>
zekno server add <name> --ssh <user@host> [--runner-path <path>]
zekno server add <name> --ssh <user@host> --runner-file <path>   (development only)
zekno server add <name> --local [--home <dir>]
zekno server update <name> [--yes]
zekno server ls
zekno secret set <NAME> [--app <app>] [--server <name>] [--stdin]
zekno secret import <file> [--app <app>] [--server <name>] [--yes]
zekno secret rm <NAME> [--app <app>] [--server <name>]
zekno secret ls [--app <app>] [--server <name>]
zekno deploy [--app <app>] [--server <name>] [-f <compose file>] [--json]
zekno rollback [--app <app>] [--server <name>] [--to <number>] [--json]
zekno status [--server <name>] [--json]
zekno logs [--app <app>] [--server <name>] [--tail <n>] [--no-follow]
zekno link [--app <app>] [--server <name>] [-f <compose file>] [--force] [--yes]
zekno settings [--json]
zekno settings set <service>.<setting> <value> [--yes]
zekno settings unset <service>.<setting> [--yes]
zekno settings compose
zekno settings init
zekno add [<template>] [--name <service>] [--for <service>] [--app <app>] [--server <name>] [--yes]
zekno add --list [--json]
zekno add <template> --show [--json]
zekno doctor [--server <name>] [--json]
zekno version [--json]
zekno --version [--json]
```

`zekno --help`, `zekno -h` and `zekno help` print this list. In a folder
linked with `zekno link`, `--app`, `--server` and `-f` come from its
`zekno.json`. Flags win over it.

At a terminal, a command that still lacks `--server` or `--app` asks for it:

```text
$ zekno status
? Which server?
  ❯ prod       deploy@203.0.113.7
    staging    this machine
  ↑↓ move   enter choose   esc leave
```

It lists your servers, then the apps on the server you chose, read from its
runner (or, when the runner cannot be reached, the apps your machine deployed
there). With one server, that server is used and named:
`Using prod, your only server.` Esc or Ctrl-C leaves the question: nothing is
done, and the command ends with "Nothing was done." and exit status 1. With no
team yet, a command other than `zekno init` and `zekno deploy` says to run
`zekno deploy` in a project folder, or `zekno init --name <you>`.

With no terminal, with `--json`, or with input piped, a command never asks: one
that still lacks a detail stops and names the flag and the project file, as
before.

Names of apps and servers are lowercase letters, digits and hyphens, starting
with a letter or a digit.

### zekno init

Creates your signing key in the system keychain and starts a team with you as
its admin. It prints the team code, which identifies your team: a server
checks it before it agrees to obey your team. If the keychain cannot take the
key, no team is created. It stops if a team already exists on your machine.

```bash
zekno init --name ada
```

### zekno server add

Connects a server: the runner sets itself up for your team, and the server is
added to your signed team list. It prints the server code, which identifies
the server's key. Teammates compare it before they trust the server.

- `--ssh <user@host>`: over SSH. `zekno` checks Docker with Compose, looks for
  a runner, and installs one when none is there (see
  [Installing the runner](#installing-the-runner)). A runner that is already
  there is used as it is, whatever its version; one that is older or newer
  than this `zekno` is reported.
- `--runner-path <path>`: use the runner already installed at that path on the
  server. Nothing is installed, and the install steps are not run.
- `--runner-file <path>`: development only. Sends a runner built on your
  machine instead of downloading a release. Not with `--runner-path`.
- `--local`: a runner on your machine. `--home <dir>` is its folder; the
  default is `runner/<name>` in the profile folder.

A runner already set up for your team by an earlier attempt that stopped half
way is carried on from. A runner that belongs to another team stops it, and
nothing is changed.

```bash
zekno server add prod --ssh deploy@203.0.113.7
```

### zekno server update

Replaces the runner on a server with the version this `zekno` carries, by the
same checked route as `server add`. At a terminal it asks first; without one
it needs `--yes`. A runner is never updated unasked. It replaces only a file
named `zekno-runner`, never replaces a newer runner, and the new runner must
answer with its version before it replaces the old one. The runner's folder,
key and state are not touched. A runner on your machine has nothing to update.

A runner newer than the one this `zekno` carries is left as it is, and you
are told to update `zekno` instead. A build of `zekno` that holds no checksum
for its runner stops with "This build of zekno has no published runner to
install", unless the runner already has this version.

```bash
zekno server update prod --yes
```

### zekno server ls

Lists the connected servers: name, SSH destination (or "this machine") and
server id.

```bash
zekno server ls
```

### zekno secret set, import, rm and ls

`zekno secret set` seals a value for one app on one server and signs it. It
takes effect on the next deploy. Before the value is asked for, `zekno` names
where it goes: `Value for NAME (api on dev): `.

- A secret value is never an argument. Leave it out and you are asked for it
  with nothing shown as you type, or pipe it in with `--stdin`. A value of
  several lines needs `--stdin`. With `--stdin`, one line break at the end is
  dropped.
- An empty value is not stored. A value may be at most 64 KiB.
- A name uses letters, digits and underscore, and does not start with a digit.
  Names the runner uses to start Docker are reserved and refused.

`zekno secret rm` signs the removal of a secret; it also takes effect on the
next deploy. `zekno secret ls` lists names and versions. No command shows a
value.

```bash
zekno secret set DATABASE_URL --app api --server prod --stdin < database-url.txt
```

`zekno secret import <file>` brings in a project's values from a file of
`NAME=value` lines, such as a `.env` file, all at once. It shows the names it
found, never a value, asks once, and stores each value sealed and signed, as
`zekno secret set` does one at a time:

```text
$ zekno secret import .env
  .env, for demo on prod

  new         DATABASE_URL, SESSION_KEY, STRIPE_KEY
  replaces    API_URL
  left out    PATH (zekno keeps this name), line 7 (not a valid name)

? Store 4 values? Values are never shown. (y/N)
✔ Stored 4 values for demo on prod. They take effect on the next deploy.
  .env still holds them in plain text. Delete it, or keep it out of git.
```

- **What is read.** One `NAME=value` per line. Blank lines and lines that
  start with `#` are skipped. `export ` in front of a name is allowed. A value
  may be in single quotes, taken exactly as written, or in double quotes, where
  `\n`, `\r`, `\t`, `\\`, `\"` and `\$` are the only escapes. A `#` after a
  space or a tab starts a comment.
- **What stops the import.** A `$` outside single quotes, a `#` inside a value
  without quotes, and a value without quotes that begins with `=`: put such a
  value in single quotes to keep it as it is.
  A value never spans lines: write a line break as `\n` inside double quotes.
  A name given twice stops it too. Any line that does not fit stops the whole
  import and nothing is stored: the message names the file and the line's
  number, and never repeats the line.
- **Names.** A name that already has a secret gets a new version
  ("replaces"). A name that does not fit the rule of `zekno secret set`, a
  reserved name, and an empty value are left out, and the rest is still
  offered. A reserved name is shown as written; any other name left out is
  shown by its line's number only (`line 7` above), since it may be the end of
  a value wrapped onto its own line. A value may be at most 64 KiB, and one
  import at most 256 values.
- **One question.** Nothing is stored before the answer, and then every value
  is stored at once, or none is. `--yes` answers the question in advance. With
  no terminal, the import stops unless you add `--yes`, and stores nothing.
  `--app` and `--server` work as for the other secret commands, and at a
  terminal are asked for when missing.
- **The file.** It may be anywhere. `zekno` reads it once, at most 1 MiB, and
  never changes, copies or deletes it. It still holds the values in plain text
  afterwards: delete it, or keep it out of git. When the file you give is a
  link, or is in a folder that is one, the first line says where it leads:
  `.env (a link to /home/ada/elsewhere/other.env), for demo on prod`.

```bash
zekno secret import .env --app api --server prod --yes
```

### zekno deploy

Signs a deploy with the next deploy number, and sends it to the runner over
one connection. What it deploys is a Compose file, or an app's settings in
`zekno.app.json` turned into Compose text on your machine (see
[zekno settings](#zekno-settings)). The first of these that applies decides
which file:

1. `-f <file>`, when given. It may be anywhere. A file named exactly
   `zekno.app.json` is read as settings, any other as a Compose file.
2. Otherwise the file a `zekno.json` signed by your team and in use here
   names, when the app is the one it names. It may be `zekno.app.json`.
3. Otherwise the one of `compose.yaml` and `zekno.app.json` in the current
   folder, when only one of them is there.
4. Both are there, and nothing above says which. At a terminal,
   `zekno deploy` asks:

   ```text
   ? Deploy from which file?
     ❯ zekno.app.json  your settings
       compose.yaml    a Compose file written by hand
     ↑↓ move   enter choose   esc leave
   ```

   Enter leaves `✔ From  zekno.app.json` (or `compose.yaml`) and goes on with
   that file. With no terminal it deploys nothing, connects to nothing, and
   stops with exit status 2:
   `This folder has zekno.app.json and compose.yaml. Say which with -f <file>.`

Neither file is ever picked over the other without you saying so. A name
counts as there even when it is a symbolic link that leads nowhere; the file's
reader then says what is wrong with it. With neither file and nothing above,
the deploy stops with
``No Compose file at <folder>/compose.yaml. Point to one with `-f <file>`.``

Except with `-f`, the file must stay inside its folder: a symbolic link out of
it is refused. Every file is read once, from one open file, and must be a
regular file: at most 256 KiB for a Compose file, 64 KiB for a settings file.
A named pipe is refused, not waited on. Do not put secrets in the Compose file
itself: it is stored and sent as written. A settings file cannot hold a
secret's value.

A settings file is read and checked whole. A fault in it, or a setting this
version does not have, stops the deploy with its sentence and exit status 1,
before anything is connected, signed or sent. From a settings file,
the text that is signed, sent and recorded is its Compose text, byte for byte
the text `zekno settings compose` prints. Rollback, status and logs work on it
as on any deploy. A service removed from the settings is stopped at the next
deploy. A volume removed from them keeps its data (see [Volumes](#volumes)).

At a terminal, the summary panel of a deploy from settings has one more row,
after `server`: the file, then its services, dim.

```text
app      demo
server   prod deploy@203.0.113.7
from     zekno.app.json  2 services: web, worker
```

A deploy from a Compose file draws the panel as before. Plain output and
`--json` are the same for both.

Exit status 1 when the runner accepted the deploy but the app did not start.
The deploy number is used either way.

```bash
zekno deploy --app api --server prod -f compose.yaml
```

At a terminal, `zekno deploy` run in a project folder first sets up what is
missing, in this order. Each thing is kept as soon as it is made. With both
files in the folder, "Deploy from which file?" is asked first, after the
question about a teammate's `zekno.json` when there is one. A fault in the
settings file is said next, before any other question.

1. Your key. It asks your name, creates the key in the system keychain as
   `zekno init` does, and shows the team code.
2. A server. It asks where the server is (`user@host`) and a name for it,
   installs the runner as `zekno server add` installs it, and shows the server
   code. With one server it uses that one and says so. With several it asks
   which.
3. The app. It offers the apps on that server, and `+ a new app` with the
   folder's name filled in. When it asked for the server or the app, it asks
   whether to remember this folder: yes writes a signed `zekno.json` naming
   the file deployed, as `zekno link` does.
4. The values the Compose file or the settings expect that have no secret
   yet. Each is asked with nothing shown as you type. Esc skips one, and the
   next run asks for it again.
5. Then the deploy.

```text
$ zekno deploy

? Your name › ada
✔ Key created. It is in your system keychain.
  Team code    J4QF-AM29-F01W-PYWM-CS8P
  Identifies your team. A server checks it before it agrees to obey your team.

✔ Docker with Compose found
✔ Runner installed  52 MB, checksum verified
✔ Added prod to the signed team list

  You reached this server over SSH, so its identity rests on SSH's host verification.

```

Esc or Ctrl-C leaves any question. What was made before it is kept, and running
`zekno deploy` again carries on from there. A detail given by a flag or by a
linked folder is never asked for. With no terminal, `zekno deploy` asks nothing
and stops as before.

### zekno rollback

Deploys an earlier service definition again, under the next number, with the
current secrets. Only deploys your machine signed and the runner answered for
count. Without `--to`, it returns to the one before the latest.

```bash
zekno rollback --app api --server prod --to 3
```

### zekno status

Reads what a server holds: its team list version, each app's last deploy and
whether it is running, and each secret's version. Never a value. When the
runner is older or newer than the one this `zekno` carries, a warning says
so, and what works until they match: an older runner is brought up to date
with `zekno server update`, and for a newer one you update `zekno`. Deploys
still work, unless the newer runner speaks a newer protocol; then you are told
to update `zekno` first.

```bash
zekno status --server prod
```

### zekno logs

Prints an app's logs, read straight from its server. `--tail <n>` is how many
earlier lines Docker sends first: 0 to 1000, 200 by default. It follows until
interrupted, or until Docker's log command or the connection ends.
`--no-follow` prints the lines Docker has and ends. Ctrl-C, or a reader that
closes the pipe (`zekno logs | head -1`), stops the reading on the server and
ends the command quietly with status 0. It needs a runner that reports its
version, as every released runner does, and an app the server has a deploy of.
Nothing is written to disk.

```bash
zekno logs --app api --server prod --tail 50 --no-follow
```

### zekno link

Writes `zekno.json` in the current folder, signs it with your key, and
records it as used on your machine. See
[The project file](#the-project-file-zeknojson).

- An app or server not given is taken from a `zekno.json` that already
  applies to the folder, only when it is signed by your team and in use here.
  From any other nothing is taken: it stops with exit status 2 and says why.
- `-f` names the file the folder deploys, a Compose file or `zekno.app.json`,
  and must be a file inside the folder. A new `zekno.json` written without
  `-f` names the one of `compose.yaml` and `zekno.app.json` that is in the
  folder. With both there it writes nothing and stops with exit status 2, at a
  terminal too, before it asks anything:
  `This folder has zekno.app.json and compose.yaml. Say which with -f <file>.`
  With neither,
  ``No Compose file at <folder>/compose.yaml. Point to one with `-f <file>`.``
- It does not overwrite a `zekno.json` without `--force`. With `--force` and
  names, it replaces any file with one signed by you.
- With no `--app`, `--server` or `-f`, a `zekno.json` signed by your team that
  already applies (in this folder or one above) is checked as one being
  written would be, and recorded as used here, not rewritten. Recording it is
  the same decision as the question every command asks the first time it
  meets a teammate's file, so `zekno link` asks it too, and only `y` records
  it: `Accepted zekno.json: <app> on <server>, file <compose>.` No stops with
  "Nothing was done." and exit status 1. With no terminal it stops with exit
  status 2 unless you add `--yes`:

  > There is no terminal to ask on. Ada linked ~/code/shop to api on prod.
  > Add `--yes` to use it here.

  A file already in use here is left as it is:
  `Already in use: zekno.json, <app> on <server>, file <compose>.` A file not
  signed by your team is refused. Names given that are exactly those of a
  signed `zekno.json` in this folder are asked about and recorded the same
  way.

```bash
zekno link --app api --server prod
```

### zekno settings

An app can be described by settings instead of a Compose file. The settings
live in `zekno.app.json`, a file in the project folder, beside the code. At
each deploy, `zekno` turns them into Compose text on your machine, and that
text is what is signed, sent and recorded, as a Compose file is. The runner
runs it as it runs any deploy. A Compose file written by hand stays possible:
a folder deploys one or the other (see [zekno deploy](#zekno-deploy) for
which).

The five `zekno settings` commands show, change, start and print the file.
None of them contacts a server, deploys or signs anything. Only
`zekno settings` itself may read the keychain, once, when the file it shows
is the one a `zekno.json` in use here names (below).

**Which file.** Every `zekno settings` command looks at the settings file
`zekno deploy` in the same folder would sign, by the same rule (see
[zekno deploy](#zekno-deploy)): the one the `zekno.json` in use here names, in
this folder or in one above, wherever it is, and named as the deploy names
it, such as `deploy/zekno.app.json`; else this folder's own `zekno.app.json`.
A `zekno.json` is in use here when your team signed it and it was used in its
folder on your machine. One that carries a signature and is not in use here
yet is what `zekno deploy` asks about first ("Use it here?"), and a yes deploys
the file it names: when that is not this folder's own `zekno.app.json`, each
command says so in one sentence and shows or changes nothing, exit status 1:
`This folder's zekno.json names deploy/zekno.app.json and is not in use on this machine yet: zekno deploy asks about it first, and a yes deploys deploy/zekno.app.json, not the zekno.app.json here.`
Nothing is asked or recorded: answer the question with `zekno link` or
`zekno deploy`. Any other `zekno.json` is left aside, as `zekno deploy` leaves
it. When the deploy would use a Compose file while a `zekno.app.json` lies
here, each command says so in one sentence and shows or changes nothing, exit
status 1:
`This folder's zekno.json names compose.yaml, so zekno deploy uses it, not the zekno.app.json here.`
With `compose.yaml` here too and no `zekno.json`, the settings are shown and
changed, and a warning says that `zekno deploy` asks which to deploy, or takes
`-f <file>`.

**Options.** The settings commands take only their own: `--json` for
`zekno settings`, `--yes` for `set` and `unset`. Any other, `--app`,
`--server` and `-f` among them, is refused with exit status 2, since it would
change nothing here: `` `zekno settings compose` does not take `--app`. `` To
see what a deploy with `--app` or `--server` would sign, run the command where
that app's folder is. A file counts only when its folder lists it exactly as
`zekno.app.json`: on a disk that ignores letter case, as macOS has by default,
`ZEKNO.APP.JSON` is not a settings file.

#### The settings file

```json
{
  "zekno": 1,
  "services": {
    "web": {
      "source": { "image": "ghcr.io/acme/demo-web:1.4.2" },
      "deploy": {
        "start": "bun run start",
        "restart": "on-failure",
        "memory": "1g",
        "cpus": 1
      },
      "networking": { "port": 3000 },
      "variables": {
        "secrets": ["DATABASE_URL", "SESSION_KEY"],
        "plain": { "NODE_ENV": "production" }
      },
      "volumes": { "uploads": "/data/uploads" }
    },
    "worker": {
      "source": { "image": "ghcr.io/acme/demo-worker:1.4.2" },
      "deploy": { "start": "bun run worker", "restart": "always" },
      "variables": { "secrets": ["DATABASE_URL"] }
    }
  }
}
```

One file describes one app, with one or more services. Each service has up to
five sections: `source`, `deploy`, `networking`, `variables` and `volumes`.
Only `source.image` is required. Any other setting, and any section, may be
left out.

| Section | Setting | What it is, and its rule |
| --- | --- | --- |
| `source` | `image` | The image the service runs, as Docker names it, such as `ghcr.io/acme/web:1.4.2`: a host if any, a lowercase path, then a tag, a digest (`@sha256:` and 64 hex digits) or both. At most 255 characters |
| `deploy` | `start` | The start command. Left out: the image's own. At most 4096 characters and 256 words, with no control or invisible character (below). It runs without a shell: see [The start command](#the-start-command) |
| | `restart` | `no`, `on-failure` or `always`. Left out: `no` |
| | `memory` | A memory limit: a whole number and `m` or `g`, such as `512m` or `1g`, at least `6m`. Left out: no limit |
| | `cpus` | A processor limit: a number above 0 and at most 1024, with at most two decimals, such as `0.5` or `2`. Left out: no limit |
| `networking` | `port` | The port the service listens on, 1 to 65535. The other services of the app reach it by the service's name |
| | `publish` | A port of the server that reaches `port`, 1 to 65535. It needs `port`, and two services cannot publish the same one. Left out: not published. See [Published ports](#published-ports) |
| `variables` | `secrets` | The names of the secrets the service reads, each set with `zekno secret set`. Never a value. Letters, digits and underscore, not starting with a digit, at most 128 characters, and not a name `zekno` keeps for itself, such as `PATH` |
| | `plain` | Values that are not secret, such as `{ "NODE_ENV": "production" }`. A name as for a secret, though a name `zekno` keeps for itself is allowed here. A value of one line with no control or invisible character (below), at most 4096 characters, which may be empty. A name cannot be both a secret and a plain variable of one service |
| `volumes` | `<name>` | A named volume, and the absolute path in the container where it is mounted, such as `/data`. See [Volumes](#volumes) |

- A service's name is lowercase letters, digits and hyphens, starts with a
  letter, and is at most 63 characters. A volume's name may also hold
  underscores.
- `"zekno": 1` is the version of settings the file is written for. A file
  written for a later version is refused:
  `zekno.app.json is written for a later version of zekno. Update zekno to use it.`
- At most 32 services. Each service reads at most 256 secret names, has at
  most 128 plain variables and 16 volumes, and mounts no two volumes at the
  same path. The services of one app read at most 256 secret names together.

**How it is read.** It is JSON, read strictly: no comment, no comma after the
last item, no key twice in one object, nested at most 6 deep, no text longer
than 4096 characters, at most 64 KiB of UTF-8. Keys may come in any order. It
is read once, with the checks a Compose file has: a regular file, and, unless
it is named with `-f`, one of yours, with one name on the disk, inside its
folder. Every command that reads it stops at the first
fault, before anything is written, signed or sent, with one sentence that
names the place and the rule, never the file's content:

```text
✖ zekno.app.json could not be read as settings.
  web, deploy.memory: use a size such as 512m or 1g.
```

Piped, it is one line on standard error. Exit status 1.

**Characters.** A start command and a plain value may hold text in any
script, accents and emoji, but no control character and no character that is
drawn as nothing or turns text around: a zero-width space or joiner, a soft
hyphen, a direction mark or override, a tag character, a Hangul filler, a
variation selector that does not follow an emoji, a line or paragraph
separator. So what `zekno` shows of a value is the value that is signed. Every
other setting takes ASCII only. A value that holds one is refused with its
place:
`web, variables.plain.NODE_ENV: use no invisible character, such as a zero-width space or a right-to-left mark.`
Nor may a plain value start or end with a space or another blank (a no-break
space, an ideographic space, a braille blank and the like), which would not be
seen at the end of a line; nor may the first or last word of a start command.
Blanks inside a value stay, and so do the spaces that only separate the words
of a start command:
`web, variables.plain.REQUIRE_AUTH: use no space or other blank at its start or end.`

**What it can never hold.** A secret's value: `secrets` is a list of names,
and the values stay in `zekno secret set`. A path on your machine: no setting
takes one. A folder of the server: a volume is a named volume. A command for
your machine: nothing in the file runs there, and `start` runs in the
container. Another file: JSON has no include, and `env_file`, `extends` and
`include` are settings this `zekno` does not know. So `zekno.app.json` holds
no secret and is safe to commit.

**Settings this version does not have.** `source.build`, `deploy.predeploy`,
`deploy.healthcheck`, `deploy.replicas` and `networking.domains` are names
kept for settings this version of `zekno` does not have. A file that sets one
is refused by every command that reads it, with two sentences that name it,
and exit status 1:

```text
✖ zekno.app.json sets a domain for web.
  Domains are not in this version of zekno yet.
```

#### The start command

The start command runs without a shell. Its words go to the container as they
are: no shell reads them, on your machine or on the server. Spaces separate
the words. A word in single quotes is taken as written; in double quotes,
`\"` and `\\` are a quote and a backslash. Outside quotes, `;`, `&`, `|`, `<`,
`>`, `(`, `)`, `$` and backquotes are refused. To use a shell, start the
command with `sh -c` and put the rest in quotes, as `sh -c "…"` or
`sh -c '…'`:

```json
"start": "sh -c 'bun run migrate && bun run start'"
```

#### Published ports

`port` alone is not published on the server: the app's other services reach
it by the service's name. With `publish`, the port is published on every
address of the server, as Compose does. It is then open to whoever can reach
the server: Docker's published ports can pass a host firewall such as `ufw`,
and Zekno does not manage the server's firewall.

#### Volumes

A volume is a named volume only. Docker keeps its data on the server under the
name `zekno-<app>_<volume>`: for the app `demo`, the volume `uploads` is
`zekno-demo_uploads`. A folder of the server cannot be mounted from settings,
so a settings file from someone else's repository cannot reach the server's
own files. To mount a folder of the server, write a Compose file:
`zekno settings compose > compose.yaml` gives one to start from. Then remove
`zekno.app.json`, or say which file with `-f`.

Removing a volume from the settings keeps its data: Compose never removes a
named volume. To delete it, run `docker volume rm zekno-demo_uploads` on the
server.

- The settings that are set are shown, and a section with none is left out.
  Secrets are shown by name, never a value.
- When the file is the one a `zekno.json` in use here names, `zekno` opens
  your team to verify it and your machine's history, which reads the keychain
  once. When your team signed it, the first line names its app, and each
  value that differs from your machine's last deploy of that app made from
  settings is marked: `! changed, not deployed (was 512m)`. Otherwise the
  first line is the file's name alone and nothing is marked.
- What that deploy had and the file no longer has is shown and marked too,
  since the next deploy drops it. A setting no longer set reads as one left
  out, dim: `memory    no limit  ! changed, not deployed (was 512m)`. A plain
  variable or a volume is a row of its own:
  `none  ! removed, not deployed (was REQUIRE_AUTH=1)`, and for a volume
  `none  ! removed, not deployed (was /var/audit; its data stays)`: removing a
  volume from the settings keeps its data (see [Volumes](#volumes)). A service
  is a line after the others:
  `auth  ! removed, not deployed (was ghcr.io/acme/auth:1)`.

Piped, one line per setting that is set: the service, the setting's place in
the file, and the value as the file holds it, separated by tabs. No marks, no
section names.

```text

web	deploy.restart	on-failure
web	deploy.memory	1g
web	deploy.cpus	1

worker	deploy.start	bun run worker
worker	deploy.restart	always
worker	variables.secrets	DATABASE_URL
```

`--json` prints the file's own data as one JSON object on one line, its keys
in `zekno`'s order, nothing added.

With no `zekno.app.json` it says
`This folder has no settings file. Run zekno settings init to start one.`
or, when the folder deploys a Compose file,
`This folder deploys compose.yaml, a Compose file written by hand, so it has no settings to show.`
Exit status 1 for both.

#### Changing one: zekno settings set and unset

`zekno settings set` changes one setting and `zekno settings unset` removes
one, named as `<service>.<setting>`:

| Setting | Also written | The value |
| --- | --- | --- |
| `image` | `source.image` | An image reference |
| `start` | `deploy.start` | The start command, as one argument in quotes |
| `restart` | `deploy.restart` | `no`, `on-failure` or `always` |
| `memory` | `deploy.memory` | A size such as `512m` or `1g` |
| `cpus` | `deploy.cpus` | A number such as `0.5` or `2` |
| `port` | `networking.port` | `1` to `65535` |
| `publish` | `networking.publish` | `1` to `65535` |
| `secrets` | `variables.secrets` | Names separated by `,` |
| `plain.<NAME>` | `variables.plain.<NAME>` | Any value, empty included. A new name is added last |
| `volumes.<name>` | | A mount path. A new volume is added last |

`set` changes a service the file has. A new service is added in the file
itself, or by `zekno settings init` for the first one. At a terminal it shows
the old and the new value and asks once:

```text
$ zekno settings set web.memory 1g
  web · memory limit  512m → 1g
? Write this to zekno.app.json? Nothing is deployed until you deploy. (y/N) yes
✔ Written  Run zekno deploy to use it.
```

- "No", Enter, Esc or Ctrl-C: `Nothing was done.`, exit status 1, and the
  file is as it was. `--yes` writes without asking.
- The question, and the sentence with no terminal below, name the file
  written as `zekno deploy` names it: `Write this to deploy/zekno.app.json?`
  for a `zekno.json` that names that file.
- With no terminal it needs `--yes`. Without it, it prints the change line,
  says ``There is no terminal to ask on. Add `--yes` to write it to zekno.app.json.``
  and ends with exit status 1. With it, the change line and
  `Written  Run zekno deploy to use it.`, exit status 0. When the file written
  is not this folder's own `zekno.app.json`, that line names it:
  `Written to deploy/zekno.app.json  Run zekno deploy to use it.`
- A value its rule refuses is said with the rule, with exit status 2, and the
  file is not touched:

  ```text
  $ zekno settings set web.memory lots
  ✖ That is not a memory limit.
    Use a size such as 512m or 1g.
  ```

  So is a change that breaks a rule across settings:
  `That change cannot be written.` then the place and the rule, such as
  `worker, networking.publish: set networking.port too, the port it reaches.`
- `unset` reads as `set` with the words of a setting left out:
  `web · memory limit  1g → no limit`. The image cannot be unset.
- A value the same as now, and `unset` of a setting not set, write nothing and
  end with exit status 0.
- A value that starts with `-` would be read as an option, as for every
  command. Put it after `--`:
  `zekno settings set --yes web.plain.NODE_OPTIONS -- --max-old-space-size=4096`.
- A setting this version does not have, such as `web.domains`, is refused with
  its second sentence: `Domains are not in this version of zekno yet.`

`zekno` writes the whole file in one layout: two spaces of indent, the keys in
a fixed order, a short object or list on one line. A file written by hand in
another layout gets that layout the first time `zekno` changes it; its meaning
does not change. The file is never left half written, and never written
through a symbolic link. It is never written over when it changed since
`zekno` read it:
`zekno.app.json changed since zekno read it, so nothing was written. Try again.`
A change runs after the next deploy.

#### What will run: zekno settings compose

Prints the Compose text the settings turn into: byte for byte the text
`zekno deploy` in this folder signs. For the file above:

```yaml
services:
  "web":
    image: "ghcr.io/acme/demo-web:1.4.2"
    command: ["bun", "run", "start"]
    restart: "on-failure"
    mem_limit: "1g"
    cpus: 1
    expose: ["3000"]
    environment:
      "DATABASE_URL": "${DATABASE_URL}"
      "SESSION_KEY": "${SESSION_KEY}"
      "NODE_ENV": "production"
    volumes:
      - type: "volume"
        source: "uploads"
        target: "/data/uploads"
  "worker":
    image: "ghcr.io/acme/demo-worker:1.4.2"
    command: ["bun", "run", "worker"]
    restart: "always"
    environment:
      "DATABASE_URL": "${DATABASE_URL}"
volumes:
  "uploads": {}
```

- Piped, the text exactly. At a terminal, the same lines, dim. To keep it,
  pipe it: `zekno settings compose > compose.yaml`.
- Every name and value is in double quotes, and a `$` in a value is written
  `$$`, so no value can change the text around it. A secret is
  `"NAME": "${NAME}"`: its value is never in the text. The runner gives it to
  Compose when it starts the app.
- The start command is the list of its words. `port` alone is `expose`; with
  `publish` it is `ports`, such as `ports: ["8080:3000"]`.

#### Starting a file: zekno settings init

At a terminal, it asks for the image and the service's name:

```text
$ zekno settings init
? Image › ghcr.io/acme/demo-web:1.4.2
? Service name › web
✔ Written zekno.app.json  Run zekno deploy to use it.
```

- It writes `zekno.app.json` in this folder with that one service and its
  image, and never over a file, not even one made while it asks. With one
  here it stops before asking:
  `There is already a zekno.app.json here. Change it with zekno settings set, or in an editor.`
  On a disk that ignores letter case, a file named `ZEKNO.APP.JSON` or the
  like takes that name: it stops before asking and says to rename it or
  remove it.
- When a `zekno.json` in use here names another file, a warning after it says
  that `zekno deploy` uses that file, not the one just made. Else, with
  `compose.yaml` in the folder too, a warning says that `zekno deploy` asks
  which to deploy, or takes `-f <file>`.
- Esc or Ctrl-C at a question: `Nothing was done.`, exit status 1. With no
  terminal it writes nothing and ends with exit status 1.

#### Exit status of zekno settings

| Status | When |
| --- | --- |
| `0` | Shown, written or printed; a value the same as now; `unset` of a setting not set |
| `1` | No settings file, or a deploy here would use a Compose file, or a `zekno.json` not in use here yet names another file; a fault in the file; "no", Esc or Ctrl-C; no terminal without `--yes`; `init` with no terminal or with a file here; the file changed since it was read, is a symbolic link, or could not be written |
| `2` | A word missing or one too many; an option the command does not take; a setting this `zekno` does not know or does not have yet; a service the file does not have; a value not allowed; a change that breaks a rule of the file; `unset` of the image |

### zekno add

Adds a ready-made service, such as a database, to this folder's
`zekno.app.json`, with the secrets it needs made on your machine.

A template is a service someone already wrote well. Each one is a data file
inside `zekno`, reviewed before it ships with a release. Nothing is downloaded
when you use one, and no template is read from your folder or your profile.
Its image is the software's official one, pinned by digest. The
[templates page](/docs/templates) lists them with their authors, and
[CONTRIBUTING.md](https://github.com/zekno-app/zekno/blob/main/CONTRIBUTING.md)
says how to write one.

| Template | Software | Made on your machine | Connection secret, for your own services |
| --- | --- | --- | --- |
| `postgres` | PostgreSQL 18.7 | `POSTGRES_PASSWORD` | `DATABASE_URL`: `postgres://app:<password>@postgres:5432/app` |
| `mysql` | MySQL 9.7 | `MYSQL_ROOT_PASSWORD`, `MYSQL_PASSWORD` | `DATABASE_URL`: `mysql://app:<password>@mysql:3306/app` |
| `mongodb` | MongoDB 9.0 | `MONGO_INITDB_ROOT_PASSWORD` | `MONGODB_URI`: `mongodb://app:<password>@mongodb:27017/app?authSource=admin` |
| `redis` | Redis 8.10 | `REDIS_PASSWORD` | `REDIS_URL`: `redis://default:<password>@redis:6379` |

Each password is 32 letters and digits, made from your system's random
source. The three databases name their user and their database `app`. Each
service restarts always, keeps its data in a volume named for it
(`postgres-data` for the service `postgres`), and publishes no port: only the
app's own services reach it, by its name. `zekno add mongo` says to run
`zekno add mongodb`.

#### Adding one

`zekno add` needs your team and a server, to seal the secrets for. With none
yet it says `There is no server to keep secrets for yet.` and
`Run zekno deploy first. It sets up your team and a server.`, exit status 2,
before any file of the folder is read. It adds to the file `zekno deploy` in
this folder would use, found by the rule of [zekno settings](#zekno-settings):
a settings file is read whole and checked; a Compose file written by hand gets
the lines to add instead (below). With neither it says
`This folder has no settings file.` and
`Run zekno settings init to start one, then add the template.`, exit status 1.
With `--app` naming another app than the folder's link, the file is this
folder's own, as for `zekno deploy --app`. With `compose.yaml` beside
`zekno.app.json` and nothing that decides, it adds to `zekno.app.json` and
warns
`This folder has compose.yaml too. zekno deploy asks which to deploy, or takes -f <file>.`,
as `zekno settings set` does: at a terminal before the summary, in a script on
standard error. The app and the server come from `--app` and `--server`, the
folder's link, or a question at a terminal, as for `zekno secret set`. It
contacts no server and deploys nothing.

At a terminal it shows what it will add, then asks once. In this folder
`zekno.app.json` has two services, so the question of who reads
`DATABASE_URL` (below) came first:

```text
$ zekno add postgres
✔ Read by  web
PostgreSQL 18.7  A relational database.                                 by zekno
╭──────────────────────────────────────────────────────────────────────────────╮
│ app     demo                                                                 │
│ server  prod deploy@203.0.113.7                                              │
│ file    zekno.app.json  2 services: web, worker                              │
╰──────────────────────────────────────────────────────────────────────────────╯
Adds a service
  postgres                postgres:18.7  pinned by digest
                          restart always · port 5432, not published
                          data kept in volume postgres-data
Makes a secret on this machine  never shown
  POSTGRES_PASSWORD       32 random characters
                          read by postgres
Builds a secret from it
  DATABASE_URL            postgres://app:••••@postgres:5432/app
                          read by web
! Zekno does not back up this data.
? Add postgres to demo? Nothing is deployed until you deploy. (y/N) yes
✔ Added postgres to zekno.app.json
✔ Stored POSTGRES_PASSWORD and DATABASE_URL, sealed for prod
  Run zekno deploy to start it.
```

- The box names the app, the server and where it is, and the file with the
  services it has now.
- **Adds a service**: the service's name in the app, its image (`--show`
  prints the whole digest), its restart rule, its port, never published, and
  its volume.
- **Makes a secret on this machine**: each password, never shown, and the
  services that read it.
- **Builds a secret from it**: the connection secret, its password drawn as
  `••••`, and the services that read it.
- Each line after `!` is a note of the template.

After a yes, the file has the service, added last, and each service that
reads the connection secret has its name last in `secrets`. The secrets are
stored as `zekno secret set` stores a value, sealed for the server, and
`zekno secret ls` lists them, not deployed. Nothing is deployed: the next
`zekno deploy` starts the database, and your app reaches it by the service's
name. `n`, Enter, Esc or Ctrl-C: `Nothing was added.`, exit status 1, and no
secret is made.

**Who reads the connection secret.** `--for <service>` names them, once per
service: `zekno add postgres --for web --for worker`. Without it, the one
other service of the file reads it, and the summary says so. With several, at
a terminal, a question comes before the summary:

```text
? Which services read DATABASE_URL?
  ❯ ◉ web
    ◯ worker
  ↑↓ move   space pick   enter done   esc leave
```

It opens with the first service picked. Space picks or unpicks. Enter with
none picked says `Pick at least one service.` and stays open. Enter leaves
`✔ Read by  web, worker`. With no terminal it never guesses:
`zekno.app.json has several services. Say which read DATABASE_URL with --for <service>.`,
exit status 2.

**`--name <service>`** gives the service another name in the app, when one of
that name is there already: `zekno add postgres --name db` adds the service
`db` with the volume `db-data`, and `DATABASE_URL` names the host `db`. A name
is lowercase letters, digits and hyphens, starting with a letter. A template
of several services takes no `--name`.

**`--yes`** adds without the question. At a terminal the summary is still
drawn.

**Refused, with nothing changed** (exit status 2 unless said):

- The app has a secret of a name the template makes or builds:
  `demo already has a secret named POSTGRES_PASSWORD.` and
  `A template can be added once to an app in this version.` A secret's name is
  the whole app's, so each template can be added once per app. `postgres` and
  `mysql` both build `DATABASE_URL`, so an app has one of the two: adding the
  second is refused this way.
- A service or a volume of that name in the file: give this one another name
  with `--name`.
- A service that would read the connection secret has a plain variable of its
  name already: remove the variable, or leave that service out with `--for`.
- A service of the file already lists in its `secrets` a secret the template
  makes or builds, whether you chose it to read the new one or not:
  `worker already reads a secret named POSTGRES_PASSWORD.` and
  `Remove it from worker.` A secret's name is the whole app's, so that service
  would read the new secret too.
- A `--for` that is no service of the file; settings that would break a rule
  of the file, such as more than 32 services or more than 64 KiB.
- The file changed while the question was open:
  `zekno.app.json changed while this was open.` and
  `Nothing was added. Run zekno add postgres again.` (exit status 1). The same
  for the app's secrets:
  `The secrets of demo on prod changed while this was open.` (exit status 1).

#### Whole or not at all

Nothing is written before everything is checked and you said yes. Then, in
this order: the file and the app's secrets are read again, to see that neither
changed; the passwords are made and every record is sealed and signed (the
keychain is read here, once); the settings file is written; the secrets are
stored, in one write. When the secrets cannot be stored, the file is put back
as it was, and `zekno` says
`The secrets could not be stored on this machine, so nothing was added.` When
even that fails, it says what is left:
`postgres was added to zekno.app.json, but its secrets could not be stored, and the file could not be put back.`
and `Remove postgres from zekno.app.json before you deploy.`

One case cannot be undone: `zekno` stopped between writing the file and
storing the secrets, by a power cut or `kill -9`. The file then has the
service, and `zekno secret ls` does not list its secrets. To finish by hand,
remove the service from `zekno.app.json`, and the connection secret's name
from the `secrets` of each service that reads it, then run `zekno add` again.
A deploy before that gives the database no password, unless you type one when
the deploy asks for it, and each of the four refuses to start without one:
none runs open.

#### A Compose file written by hand

When `zekno deploy` in this folder would use a Compose file written by hand,
`zekno add` never edits it, and never reads it. It prints the lines to add,
then makes and stores the secrets when you agree:

```text
$ zekno add postgres
This folder deploys from compose.yaml, a file written by hand.
Zekno does not edit it. Add these lines yourself.
Under services:
╭──────────────────────────────────────────────────────────────────────────────────────────────────╮
│   postgres:                                                                                      │
│     image: postgres:18.7@sha256:2ea8630df176ad090ec92136dee850397c5af8781e4bcf2e4162593691c61bbc │
│     restart: always                                                                              │
│     environment:                                                                                 │
│       POSTGRES_USER: app                                                                         │
│       POSTGRES_DB: app                                                                           │
│       POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}                                                    │
│     volumes:                                                                                     │
│       - postgres-data:/var/lib/postgresql                                                        │
╰──────────────────────────────────────────────────────────────────────────────────────────────────╯
Under volumes:  postgres-data:
In the environment: of each service that uses it
╭──────────────────────────────────────╮
│       DATABASE_URL: ${DATABASE_URL}  │
╰──────────────────────────────────────╯
? Make and store its two secrets for demo on prod? (y/N) yes
✔ Stored POSTGRES_PASSWORD and DATABASE_URL, sealed for prod
```

- Put the service's lines under `services:`, the volume under the top-level
  `volumes:`, and the connection secret's line in the `environment:` of each
  service that uses it. The volume is named `<service>-<volume>`, as in a
  settings file: `postgres-data`, or `db-data` with `--name db`.
- A `$` in a value is written `$$`, so Compose leaves it for the container,
  and each secret is `${NAME}`: the runner gives Compose its value when it
  starts the app. No value is ever in the lines.
- The secrets are made and stored as for a settings file, and refused the
  same way when the app has a secret of one of their names. `--for` is
  refused: you add the line to the services you choose. A no, Esc or Ctrl-C:
  `No secret was made.`, exit status 1.
- Piped, it prints the service's lines and the connection secret's lines
  exactly as you would type them, with no box and no words around them. It
  does not print the volume to declare: add it under the top-level `volumes:`
  yourself (`postgres-data:` for postgres), since Compose refuses a service
  that names a volume nobody declared. Without `--yes`, it then says
  `Making its secrets stores them on this machine. Say --yes to go ahead.` on
  standard error, exit status 1, and makes nothing. With `--yes`, one line
  follows for each secret stored, such as `stored	POSTGRES_PASSWORD	1`.

#### With no terminal (scripts)

`zekno add` never asks. Without `--yes` it stops, exit status 1, and changes
nothing:
`Adding a template changes zekno.app.json and stores secrets. Say --yes to go ahead.`
on standard error. With `--yes` it adds, and prints one line for each thing
done, with tabs: the file it changed, then each secret and the version it got.

```bash
zekno add postgres --yes --app demo --server prod --for web
```

```text
added	postgres	zekno.app.json
stored	POSTGRES_PASSWORD	1
stored	DATABASE_URL	1
```

`--app` and `--server` come from the flags or the folder's link. One that is
missing stops it with the sentence the other commands use, such as
``Say which app with `--app <name>`, or link this folder to it with `zekno link`, which keeps it in zekno.json.``
Every refusal is one line on standard error, its two sentences joined by a
space.

#### What it does not do

- **Zekno does not back up the data.** Back it up yourself.
- **The data is kept in a Docker volume on your server**, named
  `zekno-<app>_<volume>`: for the app `demo`, the service `postgres` keeps it
  in `zekno-demo_postgres-data`.
- **The image changes only with a new `zekno`.** Each template names one image
  by its digest. A newer image comes with a newer release of `zekno`, in a
  template that changed.
- **Nothing is deployed until you deploy.** Adding writes `zekno.app.json` and
  the secret store on your machine, and nothing else.
- **No command removes a template's service.** To remove it, edit
  `zekno.app.json`: take out the service, and the connection secret's name
  from the `secrets` of the services that read it. The next deploy stops the
  service. Its volume is never deleted, by `zekno` or by Compose: to delete
  its data, run `docker volume rm zekno-demo_postgres-data` on the server. Its
  secrets stay stored for the app until you remove them with
  `zekno secret rm`. A volume you keep holds the database as it was:
  PostgreSQL, MySQL and MongoDB take their password only when they start on an
  empty volume, so they keep the first one.

MongoDB's template makes the database's administrator only, since its image
can make no other user without a script mounted from the server: your app
connects as the administrator (`MONGO_INITDB_ROOT_USERNAME` is `app`). Its
image also declares a second volume, at `/data/configdb`. A single server
leaves it empty, and Docker gives it a volume with no name.

Redis has no variable for its password. Its template starts it with one short
line, run inside the container, that writes the password from the secret into
a file only Redis can read, then starts Redis with that file. The password is
on no command line.

#### Exit status of zekno add

| Status | When |
| --- | --- |
| `0` | Added; listed; shown; the hand-written lines printed and their secrets stored |
| `1` | No settings file; a fault in the settings file; no terminal without `--yes`; "no", Esc or Ctrl-C; the file or the app's secrets changed while it was open; the secrets could not be stored; more secrets than a deploy carries or this machine keeps; a refusal of the keychain or of signing; a question of the app or server left |
| `2` | A word or an option it does not take; a `--name` that is not a service name; no template of that name; no server yet; a secret, service, volume or variable that is there already; several services and no `--for` with no terminal; a `--for` that is no service of the file; settings that would break a rule of the file; a template that asks a question |

### zekno doctor

Checks this machine and each connected server, one line per check, and says
what to do for each thing that is wrong. zekno itself changes nothing, on your
machine or on any server. SSH keeps its own records: it may add the server to
`known_hosts` on your machine, and the server logs the login.

```text
$ zekno doctor
  This machine
✔ zekno          0.1.0, installs runner 0.1.0
✔ Key            in your system keychain
✔ Profile        verified, team list v2
✔ This folder    linked to demo on prod, compose.yaml is readable

  prod  deploy@203.0.113.7
✔ Reachable      over SSH
✔ Docker         Compose 5.6.0
! Runner         0.1.0-dev.1, older than this zekno's 0.1.0
                 Run zekno server update prod
✔ Disk           133 GB free

  staging  deploy@198.51.100.4
✖ Reachable      SSH needs an answer
                 Open zekno and press enter on staging
–  Docker        not checked
–  Runner        not checked
–  Disk          not checked

  1 problem, 1 warning.
```

- **This machine.** `zekno`'s version and the runner release it installs; the
  key (in the system keychain, and the one the profile names); the profile (it
  verifies, and its team list version); and this folder, when it has a
  `zekno.json` or a `compose.yaml` (the link is signed by your team and used
  here, and the Compose file can be read). It does not check the settings in a
  `zekno.app.json`: `zekno settings` does.
- **Each server.** Whether it can be reached; Docker with Compose, and its
  version; the runner, and how its version stands to this `zekno`'s; and the
  free disk space where the runner keeps its state. It finds these with a short
  fixed script that only reads, and by asking the runner its version and
  status.
- **Results.** `✔` good, `!` a warning, `✖` a problem, `–` not checked: a check
  that depends on one that failed is not checked, not wrong. Every warning and
  problem has a line under it that says what to do. A warning does not fail
  the command; only a problem does, with exit status 1.
- **No questions.** It reaches servers in SSH's batch mode and never asks for
  anything, so it never waits on a password. A server where SSH would have to
  ask says "SSH needs an answer": open the app with `zekno` and press `enter`
  on that server, where SSH can ask.
- **zekno changes nothing.** zekno writes no file on your machine,
  `links.json` included; it writes, installs and starts nothing on a server; no
  deploy number is used. SSH's own records are as said above.
- `--server <name>` checks your machine and that one server. `--json` prints
  one object: `zekno`, `runner`, `machine` (the checks of your machine),
  `servers` (each with `name`, `where` and `checks`), `serversSkipped`,
  `latest`, `problems` and `warnings`. Each check has `check`, `result`
  (`good`, `warning`, `problem` or `not_checked`), and `detail` and `next`
  where there are any.
- It also asks GitHub once whether a newer release exists, as `zekno version`
  does. A newer one makes the `zekno` line a warning, with "A newer release
  exists" under it; no answer is not a warning.

```bash
zekno doctor --server prod
```

### zekno version

Prints the version of this zekno and of the runner release it installs.
`zekno --version` prints the same. With `--json`, one object:
`{"zekno":"0.1.0","runner":"0.1.0"}`. It needs no key, no profile and no
terminal, and changes nothing.

`zekno version` then asks GitHub once whether a newer release exists, and says
so in one more line:

```text
$ zekno version
zekno 0.1.0
runner 0.1.0, the runner release this zekno installs
✔ This is the newest release.
```

When a newer release exists, the last line is a warning instead: "! A newer
release exists: 0.2.0. Update zekno to get it." When it could not find out, it
is a dim `Could not check for a newer release.`: no network, no answer within 3
seconds, or an answer that is not a version. The exit status is 0 in each case.
With `--json` the answer is the field `latest`, whose `state` is `newest`,
`newer` (with the `version`) or `not_checked`:
`{"zekno":"0.1.0","runner":"0.1.0","latest":{"state":"newer","version":"0.2.0"}}`.

- It reads one small file from `raw.githubusercontent.com`, GitHub's host for
  files in a repository: the runner release file on the `main` branch of
  `zekno-app/zekno`, within 3 seconds. A newer version counts only once both
  its checksums are in that file, so a release that cannot be installed yet is
  not announced. `zekno --version` never uses the network.
- The request carries the name `zekno` and nothing about you, your team, your
  servers or your project. GitHub learns the address and the time of the
  request.
- Only `zekno version` and `zekno doctor` contact GitHub, at
  `raw.githubusercontent.com`, each once per run. Nothing else in zekno does so
  on its own, there is no check in the background, and nothing is stored.
- zekno never downloads or installs a newer release. Until zekno is packaged,
  updating it means getting the newer source and building it again: see
  [Build from source](#build-from-source).

### Exit status

| Status | Means |
| --- | --- |
| `0` | Success. Also the app when you quit, and `zekno logs` stopped with Ctrl-C or a closed pipe |
| `1` | Refused or failed, including a deploy whose app did not start, and a question left with Esc or Ctrl-C |
| `2` | Wrong usage, including a `zekno.json` not signed by your team, one not used here yet when there is no terminal to ask on, `zekno` with no arguments and no terminal, a folder with both `zekno.app.json` and `compose.yaml` and nothing to say which when there is no terminal to ask on, and a setting value not allowed |

### Output

At a terminal, single commands use the app's symbols, wording and panels.
`zekno deploy` and `zekno rollback` show the summary panel, the stage row and a
result line with what to run next; a failed start shows what Docker reported.
Over SSH nothing is animated, because SSH may ask for a password in the same
terminal.

When standard output or standard input is not a terminal (piped, in a script,
`< /dev/null`), with `TERM=dumb` or with `--json`, commands print plain lines:
results on standard output with table cells separated by tabs, warnings and
failures on standard error, no colour, symbols or panels.
With `--json`, one JSON object. That form is stable, and these are the changes
from the first version:

| Command | Plain output | Changed from the first version? |
| --- | --- | --- |
| `deploy`, `rollback` | `Deploy <n> of <app> is running on <server> with <k> secrets.` | Yes: "`<k> secret(s)`" became "`<k> secrets`", "`1 secret`" or "`no secrets`" |
| `deploy --json` | `{"outcome","app","sequence","server"}` | No |
| `status` | `<server>: team list version <v>`, then `<app>\tdeploy <n>\t<state>`, then `<app>/<NAME>\tversion <v>` | Yes: a third cell, `running`, `stopped`, `partly running` or `unknown`; the apps in Home's order, the latest deploy from your machine first |
| `status --json` | As before, plus `"apps": { "<app>": { "state", "services": [...] } }` | Yes: one added field |
| `secret ls`, `server ls` | Unchanged | No |
| `logs` | `<time>\t<service>\t<text>`, one line per log line | New |
| `settings` | `<service>\t<place>\t<value>`, one line per setting that is set | New |
| `settings --json` | The file's own data, one object | New |
| `settings set`, `settings unset` | `<service> · <label>  <old> → <new>`, then `Written  Run zekno deploy to use it.` | New |
| `settings compose` | The Compose text, byte for byte | New |

Docker's output is not printed during a deploy. On a failed start in plain
mode, the lines Docker reported are written to standard error after the
failure sentence.

A script that gives zekno a terminal on both ends (`expect`, `script`,
`docker run -t`) gets the questions a person gets. Pass `--server` and
`--app`, or `--json`, or `< /dev/null`, so that nothing waits on a question.

Lines that a runner, Docker or SSH write on standard error are passed on after
the mark `remote:`, so they cannot pass for the tool's own. One place has no
mark: at a terminal, `zekno deploy` and `zekno rollback` show Docker's latest
line dim and set in by two columns under the stage row, and on a failed start show
Docker's lines inside a panel titled "Docker said". Those lines are the
server's words, not the tool's. Text from a server is cleaned of terminal
control sequences before it reaches the terminal, in the app and in single
commands.

## The project file: zekno.json

```json
{
  "app": "api",
  "server": "prod",
  "compose": "compose.yaml",
  "signed": { "payloadType": "zekno.link.v1", "payload": "...", "signature": { "keyId": "...", "sig": "..." } }
}
```

It saves typing `--app`, `--server` and `-f` in a project folder. It holds
three names and your team's signature of them, nothing else: no secret and no
key (the signature and the key id are public), so committing it gives
nothing away. Its signature vouches for the names (which app, which server,
which file), not for what the file says. Whatever is checked out in a linked
folder is what `zekno deploy` deploys there, so read a branch, such as a pull
request's, before you deploy it.

| Field | Rule |
| --- | --- |
| `app` | An app name: lowercase letters, digits and hyphens |
| `server` | A server name, same rule. It must be a server connected on your machine when used |
| `compose` | The file the folder deploys: a Compose file, or `zekno.app.json`. A relative path inside the folder that holds `zekno.json`. No `..`, not absolute. Without `-f`, `zekno link` writes the one of `compose.yaml` and `zekno.app.json` that is there |
| `signed` | The signature `zekno link` adds: a member of your team signed this app, server and file |

When `compose` names a file called `zekno.app.json`, a deploy reads it as
settings and signs the Compose text they turn into, so the settings are signed
at each deploy, as a Compose file is. Every member of your team who deploys
such a folder needs this `zekno` or later: an older `zekno` reads the settings
file as a Compose file and signs it as it is, the runner accepts that deploy,
and Compose refuses the text on the server, so the app does not start.

- An unknown field is an error, and so is a field written twice.
- It is looked for in the current folder, then each folder above it, stopping
  at your home folder or the filesystem root. A folder above your home folder
  is never read.
- Only a regular file named exactly `zekno.json`, of at most 4096 bytes, that
  belongs to you is used. A symbolic link, a pipe or another user's file is an
  error that names it.
- It is written only by `zekno link` or a "yes" in the app, signed with your
  key, never over an existing one without `--force`, as a whole file with
  mode 644.

### Linking a folder

Run `zekno link --app <app> --server <server>` in the folder, or answer yes
to "Remember this folder?" in the app. Commit the `zekno.json` it writes.
From then on, in that folder and the folders below it, `zekno deploy`,
`rollback`, `status`, `logs` and `secret` need no `--app` or `--server`, and
the app opens on that app.

Two things must both be true before zekno uses a `zekno.json`:

1. **Someone in your team wrote it.** Its signature is checked against your
   verified team list, as it is now. A file with no signature, one from
   another team, one signed by someone since removed from the team, one
   edited by hand after it was signed, or one signed for a server of another
   name is not signed by your team. It is refused outright and never offered:

   > zekno.json in ~/code/shop is not signed by your team, so zekno does not
   > use it. It names api on prod. To link this folder yourself, run
   > `zekno link --app <name> --server <name> --force`. To leave the file
   > aside, give --app and --server.

   With no terminal a command stops with exit status 2. At a terminal it
   names the file with its first two sentences, leaves it aside, and asks for
   the server and the app as if it were not there; `zekno link` without
   `--force` stops instead, since writing would replace the file. The app
   shows the first two sentences on Home, selects nothing, and `d` deploys
   nothing.
2. **You used it in this folder on your machine before, or you say yes
   once.** A signature proves who wrote a file, not where it is: anyone who
   can read a repository can copy its `zekno.json` into another folder beside
   another Compose file. So the first time a teammate's file is met in a
   folder, zekno shows what it names and asks once. At a terminal:
   `Ada linked this folder to api on prod. Use it here?` Only `y` goes on;
   anything else stops with "Nothing was done.". A file in a folder above is
   named with that folder and the Compose file a yes deploys:
   `Ada linked ~/Downloads to api on prod, with ~/Downloads/compose.yaml. Use it here?`
   In this folder, the file a yes deploys is named when it is not
   `compose.yaml`:
   `Ada linked this folder to api on prod, with deploy/zekno.app.json. Use it here?`
   (the app's own question names no file).
   When `--app` or `--server` sends the command elsewhere than the file names,
   the question says both:
   `Ada linked this folder to api on dev. This command uses api on prod. Use it here?`
   A key typed before the question is drawn, such as while the keychain asks,
   is thrown away: only a `y` typed at the question answers it. `zekno link`
   asks the same question. The app asks when it opens, with `y use it` and
   `n not now`. With no terminal the command stops with exit status 2:

   > Ada linked ~/code/shop to api on prod, and it has not been used in this
   > folder on this machine. To use it, run `zekno link` there once and answer
   > its question, or `zekno link --yes` from a script. To leave it aside, give
   > --app and --server.

What you have used is recorded in `links.json` in the profile folder: the
real path of each file and the SHA-256 of its bytes. Any change to its bytes,
such as a teammate's new link arriving with a `git pull`, is asked about once
more. Given both `--app` and `--server`, a command leaves the file aside
unless it is in use here, and never asks; a file that cannot be read (a link,
another user's file, not valid JSON) then counts as no `zekno.json`.
`links.json` is not signed, on purpose: someone who can write your profile
folder and also plant a project folder gains nothing from it they do not have
already, and an entry alone never makes a file count.

Its file goes with its app. With `--app` naming another app, the file is
`-f`, or the one of `compose.yaml` and `zekno.app.json` in the current folder,
as without a project file.

## Installing the runner

`zekno server add <name> --ssh <user@host>` with no `--runner-path` runs a
fixed shell script on the server over SSH. It stops at the first step that
fails, and installs nothing unless every check before it passed:

1. Connect.
2. `docker compose version` must work.
3. Look for a runner: at `/usr/local/bin/zekno-runner` (root) or
   `~/.local/bin/zekno-runner` (any other user), then on the `PATH`. One that
   is found is used as it is; skip to step 8.
4. The server must be Linux on x86-64 or ARM64.
5. The server must have a C library the runner can use. When
   `getconf GNU_LIBC_VERSION` names glibc older than 2.17, or `ldd --version`
   names musl, it stops here. A server that answers neither goes on, and step
   7 catches a runner that cannot start.
6. `sha256sum` or `shasum` must be there. Then the release file is downloaded
   with `curl` or `wget` into a new private temporary folder beside where the
   runner goes, and unpacked. The download goes over HTTPS only, and follows a
   redirect only to another HTTPS address. With `--runner-file`, the file
   `zekno` sends is read instead, and step 7 checks it against the SHA-256
   `zekno` computed before sending it.
7. Its SHA-256 must equal the value this `zekno` holds. The value never comes
   from the download or from the server. The new runner must then answer
   `version` with the expected version from the temporary folder. Only then
   is it moved into place, with mode 755.
8. `zekno-runner version` must answer with the expected version, when it was
   just installed or was found at this version.
9. Create the runner's folder with mode 700 if it is missing.

The runner then sets itself up for your team over the same connection.

| Who you log in as | Runner | Its folder |
| --- | --- | --- |
| root | `/usr/local/bin/zekno-runner` | `/var/lib/zekno` |
| any other user | `~/.local/bin/zekno-runner` | `~/.local/state/zekno` |

The script never uses `sudo`. The server needs `sh`, `uname`, `curl` or
`wget`, `gzip`, `sha256sum` or `shasum`, Docker with Compose, and to reach
github.com over HTTPS. A runner release is a GitHub Release of the
[repository](https://github.com/zekno-app/zekno), with one file for each kind
of processor.

### Which runner it installs

A build of `zekno` installs exactly one runner version, with the SHA-256 of
the runner for each kind of server. Which one depends on the branch that build
of `zekno` came from. You never choose it.

| `zekno` built from | Installs | Its version | On GitHub |
| --- | --- | --- | --- |
| `main` | a prod release | three numbers, such as `0.1.0` | a release |
| `dev` | a development release, for trying a runner on a real server before the prod release | three numbers and `-dev.<n>`, such as `0.1.0-dev.1` | a pre-release, never shown as the latest |

A development version is older than the prod version with the same three
numbers. So a `zekno` built from `main` brings a server that runs
`0.1.0-dev.1` up to `0.1.0` with `zekno server update`, and a `zekno` built
from `dev` never replaces that `0.1.0` with a development release of the same
numbers. When one of the two is a development release and the other is not,
`zekno status`, `zekno server add` and the app say so after they say which is
older.

When you work on `zekno` itself, your build installs the release your
branch's `apps/cli/src/version/runner-release.json` names, not the runner in your
checkout. To try a runner you changed, build it and send it with
`--runner-file` (below); it must answer with the version your `zekno`
carries.

### How a release is trusted

The checksums a build of `zekno` holds are written by one command only: the
maintainer's second build. After GitHub's workflow has built and published a
release, the maintainer builds the same commit again on their own machine,
with the same Bun version, and compares each runner three ways: their own
build, the file GitHub published, and the release's `SHA256SUMS`. Only when
all three agree are the checksums written, and committed on the branch of
that release. Development releases are checked the same way. The release
procedure is `apps/runner/RELEASING.md` in the
[repository](https://github.com/zekno-app/zekno).

The second build proves that the published file is what this source and this
build tool produce, so GitHub's build service did not change it. It does not
prove that the build tool or the dependencies are good: both builds use the
same Bun version, the same npm packages (pinned by `bun.lock`) and the same
Bun runtimes for Linux, so a fault in those would be in both.

Releases are not signed, and no record of how they were built (build
provenance) is published yet. What a server relies on is the checksum your
`zekno` holds: it installs a download only when its SHA-256 equals that value.

### Supported servers

The runner is built for:

- Linux on x86-64, with a processor that has SSE4.2: Intel Nehalem, AMD
  Bulldozer or newer.
- Linux on 64-bit ARM (ARM64).
- The GNU C library (glibc) 2.17 or newer: Debian, Ubuntu, RHEL and similar.
  Alpine and other systems with the musl C library are not supported yet.

The download is about 52 MB, and the runner about 110 MB on disk. While it
installs, both are side by side where the runner goes, so keep at least
256 MiB free there.

What was tried, and what was only read: on 2026-11-14 the install script ran
in local containers, as root, with the runner file sent after it as
`--runner-file` does. The runner started on Debian 12 on ARM64 and on x86-64
(emulated), and on CentOS 7, which has glibc 2.17, on both. On Alpine the
install stopped before the file was read, as it should. Containers stand in
for the C library and the kind of processor only. The processor floor
(SSE4.2) comes from Bun's documents and was not tried, and no old kernel was
tried. What each release was tried on is added to its release notes.

### When it stops

Each way the install can stop says what happened, and leaves the server as
it was:

| When | `zekno` says |
| --- | --- |
| No Docker with Compose | Docker with Compose was not found on the server. Install Docker with its Compose plugin there, then try again. |
| Not Linux on x86-64 or ARM64 | This kind of server is not supported yet. The runner is built for Linux on x86-64 and ARM64. |
| glibc older than 2.17, or musl; or the new runner cannot find its C library | This server does not have the GNU C library (glibc) 2.17 or newer that the runner needs. Alpine and other Linux systems with musl are not supported yet. Nothing was installed. |
| This `zekno` holds no checksum for that kind of server | This build of zekno has no published runner to install. It goes on to name the two ways in [If this zekno holds no checksum](#if-this-zekno-holds-no-checksum). |
| Neither `sha256sum` nor `shasum` | The server has neither sha256sum nor shasum to check the runner with, so nothing was downloaded or installed. |
| The download or unpacking failed, with less than 256 MiB free | The server ran out of disk space for the runner. It needs at least 256 MiB free in /usr/local/bin as root, or in ~/.local/bin for another user. Nothing was installed. |
| The download or unpacking failed otherwise | The server could not download the runner. It needs curl or wget, gzip, and to reach github.com over HTTPS. |
| The SHA-256 differs | The downloaded runner did not match the checksum this zekno holds. It was deleted and nothing was installed. |
| The new runner was stopped by an instruction the processor lacks | This server's processor cannot run the runner. On x86-64 it needs SSE4.2: Intel Nehalem, AMD Bulldozer or newer. Nothing was installed. |
| The new runner did not answer for another reason | The runner did not start on the server: it did not answer with version `<version>`. |

In `zekno server update`, the four for glibc, `sha256sum`, disk space and the
processor end with "The runner that was there is still in place." instead.
When the new runner wrote something before it failed, its first line is shown
too, as a line from the server: after `remote:` in a single command, and in
the full output in the app.

### If this zekno holds no checksum

A `zekno` that holds no checksums has no published runner to install. That
is so between a release and its second build, after a release was withdrawn,
and before a branch's first release is recorded. `zekno server add` still
uses a runner already on the server. Otherwise, use one of these:

- Install the runner by hand, as the
  [runner page](/docs/runner#install-on-a-server) describes. A runner at the
  places in step 3 is found and used. Anywhere else, add the server with
  `--runner-path <path>`.
- For development, `--runner-file <path>` sends a runner you built. Its
  SHA-256 is computed on your machine and checked on arrival, and it must
  answer with the version this `zekno` carries. A runner already on the
  server is used as it is, also with `--runner-file`.

### Limits of this route

From the reviews:

- A release is trusted through the checksum your `zekno` holds, not through a
  signature. The second build shows that GitHub's build service changed
  nothing; it does not check Bun or the npm packages both builds use.
- With `wget`, the download has no size limit, and `curl` before 8.4 does not
  stop a download of unknown length. Only whoever serves the release address
  over TLS could use that to fill the disk.
- "Installed the runner … It matched the checksum" repeats what the server
  printed. A server that lies can print it without doing it. What the server
  is trusted for is decided by the session that follows, where every answer is
  checked.
- Before the first `zekno server add`, someone who can write to a folder on
  the `PATH` of the user you log in as could put a `zekno-runner` there, and it
  would be used.
- `--runner-file` checks the file, then reads it. A file swapped in between is
  read without the size limit. It is a development option.
- Installing as root has no automated test yet. It was tried by hand in the
  local containers above.
- An x86-64 processor without SSE4.2 was not tried. The installer reads a
  runner stopped by an illegal instruction as the processor's lack; whether
  the runner stops that way on such a processor is not known.

## What is kept where

On your machine:

| What | Where |
| --- | --- |
| Your signing key and the team code | The system keychain, service `app.zekno.cli`. Never in a file; there is no option for that. |
| Team lists, connected servers | `~/.zekno/profile.json` (or `ZEKNO_HOME`). Public keys and signatures only. |
| Secrets | `~/.zekno/secrets/<server id>/<app>.json`, as encrypted, signed records. A value cannot be shown again after it is set. |
| Deploy history | `~/.zekno/history/<server id>/<app>.json`: the last 50 signed deploys of each app, for rollback. |
| Project files used here | `~/.zekno/links.json`: the real path and SHA-256 of each `zekno.json` used on your machine, at most 500. |
| A runner on your machine | `~/.zekno/runner/<name>`, unless `--home` named another folder. |
| Which app a folder deploys | `zekno.json` in the project folder. |
| An app's settings | `zekno.app.json` in the project folder, beside the code. It names secrets but never holds a value, so it is safe to commit. |

The profile folder has mode 700 and its files mode 600. App state and logs are
never stored.

Changing a setting, with `zekno settings set`, `unset` or `init` or on the
settings screen, writes `zekno.app.json` and nothing else, and contacts no
server. The change runs after the next deploy, whose signed text is in the
deploy history like any other. `zekno add` writes `zekno.app.json` and stores
the app's new secrets, and contacts no server. A Compose file written by hand
is never written: only the secrets are stored.

The file you give `zekno secret import` is read once and never copied: its
values are kept only as the encrypted records above. `zekno doctor` itself
writes nothing, on your machine or on a server. SSH keeps its own records: it
may add the server to `known_hosts` on your machine, and the server logs the
login.

The files in `~/.zekno` are safe to read but are not believed as they stand.
Every command rebuilds the team from the signed team lists, starting from the
team code in the keychain, and checks each secret and each history entry
against it. A file changed by something other than `zekno` is refused or
ignored, never signed. The folder holds no command to run.

On the server, see the [runner page](/docs/runner#its-folder).
