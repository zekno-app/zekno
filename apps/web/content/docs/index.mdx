## What Zekno is

Zekno gives a team the convenience of a managed platform (a desktop app,
teammates with roles, deploy history) on servers they own, starting with
Hetzner and Docker Compose.

It is built so that a full compromise of the Zekno service yields no customer
secrets and no ability to run code on customer servers.

| Property | What it means |
| --- | --- |
| **Client-side encryption** | Secrets are encrypted on your machine. The hosted service only ever stores ciphertext. |
| **Signed deploys** | Every deploy is signed on your machine. Your servers refuse anything your team didn't sign. |
| **Auditable client code** | Everything that runs on your side is in the public repository. |
| **No runtime dependency** | Your servers don't need Zekno to keep your apps running. |

## The three parts

| Part | Runs on | Keys it holds | Sees plaintext secrets | Can authorize a deploy |
| --- | --- | --- | --- | --- |
| Desktop app | A team member's machine | Team signing key | Yes | Yes |
| Control plane | Zekno's infrastructure | None | No | No |
| Runner | Your server | Server decryption key | Yes | No, it only verifies |

## How a deploy works

1. **Encrypt.** The desktop app encrypts each secret for your server's public key before anything leaves your machine.
2. **Sign.** The app signs the deploy with your team's key.
3. **Relay.** The control plane stores the sealed, signed packet. It has no key to open it. Your server's runner pulls it over an outbound connection.
4. **Verify.** The runner checks the signature before doing anything, and refuses a deploy your team did not sign.
5. **Run.** The server decrypts with its own key and starts your containers.

## What it protects against

| Scenario | Outcome | Why |
| --- | --- | --- |
| An attacker copies the Zekno database | No secrets exposed | It holds only ciphertext |
| An attacker controls Zekno and pushes a deploy | Deploy rejected | Servers reject anything not signed by a team key |
| Zekno goes down | Apps keep running | Servers don't depend on it at runtime |

## What it does not protect against

| Scenario | Why |
| --- | --- |
| A team member's machine is compromised | That machine holds a signing key |
| One of your servers is compromised | Secrets are plaintext in memory where the app runs |
| A Zekno app or runner release is tampered with | The client is the trust anchor. A server installs a runner only when it matches the checksum the command-line tool holds, recorded after a second build of the same source gave the same file. Runner releases are not signed |

<Callout title="Metadata">
  The control plane still sees metadata: server addresses, app names, deploy
  times and team membership.
</Callout>

## What exists today

| Part | Status |
| --- | --- |
| Website (`apps/web`) | Landing page and these docs; the signed-in dashboard is planned |
| Core library (`packages/core`): encryption, signing, team lists, message formats | First version built; internal review only |
| Command-line tool (`apps/cli`) | Second version built: a full-screen terminal app and single commands for scripts, running state and logs read from your server, and a project file. One developer, deploying directly over SSH. It installs on a server the runner release its build carries, checked against a checksum it holds. The first runner release, 0.1.0, is published. Internal reviews only. See [Command-line tool](/docs/cli) |
| Server runner (`apps/runner`) | Second version built: verifies, decrypts, starts Docker Compose, and reports running state and logs without changing anything. One connection per command. Built for Linux on x86-64 and ARM64 with glibc 2.17 or newer. Internal reviews only. See [Server runner](/docs/runner) |
| Desktop app (`apps/desktop`) | Planned |
| Control plane | Hosted by Zekno, closed source |

Everything that runs on your device or in your browser is open source under
the MIT license. The control plane is closed because it is the hosted service
Zekno sells; the design means you don't have to trust it.

## Status and limits

- **One developer on one machine.** Teammates arrive with the control plane,
  which is not written yet.
- **SSH is the route.** `zekno` talks to the runner directly, over SSH. No
  Zekno service is involved.
- **Only `zekno version` and `zekno doctor` reach the network on their own:**
  each asks GitHub once for the newest release, and sends nothing about you.
- **State and logs come from your server.** Whether an app is running, and its
  logs, are read from the runner over SSH when you look. They never pass
  through Zekno, and your machine keeps none of it.
- **The runner comes from a release.** `zekno server add` installs on a
  server the one runner version your build of `zekno` carries, and only when
  it matches the checksum that build holds. A `zekno` built from `main`
  installs a prod release, such as `0.1.0`; one built from `dev` installs a
  development release, such as `0.1.0-dev.1`. See
  [Installing the runner](/docs/servers#installing-the-runner).
- **The first runner release is 0.1.0.** A `zekno` built from `main` holds its
  checksums and installs it on a server by itself. Between a release being
  started and its second build, a `zekno` built from that branch holds no
  checksums and says it has no published runner to install.
- **Docker's messages are shown as they are.** An error from Docker can repeat
  a value that was filled in from a secret.
- **App settings cover an image that is already built.** This version cannot
  build an image from source, serve a domain with HTTPS, wait for a health
  check, run a command before a deploy, or run several copies of a service. A
  `zekno.app.json` that sets one of them is refused with a sentence that names
  it. A Compose file written by hand can do what Compose does.
- **A published port is open to whoever can reach the server.** It is
  published on every address of the server, as Compose does, and Docker's
  published ports can pass a host firewall such as `ufw`. Zekno does not
  manage the server's firewall.
- **"Changed, not deployed" knows only your machine's deploys.** A teammate's
  later deploy from another machine is not seen.
- Made for macOS and Linux with a system keychain. Windows is not tested.

The internal security reviews, which say what was checked and what was not,
are in the `specs` folder of the
[repository](https://github.com/zekno-app/zekno).
